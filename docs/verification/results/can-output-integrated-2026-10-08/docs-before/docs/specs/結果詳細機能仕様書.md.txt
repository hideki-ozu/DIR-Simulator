[評価結果の取得の親要件](../要件定義書.md#dir-req-0008)は、時系列、集計、保存形式と診断を同じ実行へ対応付けて満たす。本書の入力は[実行仕様](実行詳細機能仕様書.md#event-order)の成功コミット済みjournal、凍結した終了境界と確定条件である。モデルが通知した実到達点と資源遷移から計測・集計を作り、CSV／JSONとmanifestを出力する。[診断仕様](診断詳細機能仕様書.md#termination)が終了状態と診断の意味を定める。

親要件の判定では、要求ID・対象・単位・時刻／区間を使い、モデルの状態、時系列標本、集計値、読み戻したCSV／JSONを照合する。CANの送信成功と受信完了は別の観測点であり、一送信・複数受信を同じ母数へ合算すると保存則が崩れる。子要件の個別指標の確認に加え、要求台帳と受信台帳それぞれの件数・未完了状態が集計と一致することを確認する。

| 対象 | 確定規則 |
| --- | --- |
| 分担 | [時系列記録](../機能仕様書.md#dir-func-0018)を具体化する。時間・順序は実行詳細仕様、送受信条件はCAN詳細仕様を正とし、本書は観測と保存形式を定める。 |
| 時刻 | シミュレーション開始を0とするu64の整数ps。`generated_ps=g`、送信処理終了・キュー受理判定`ready_ps=q`、送信開始`sof_ps=s`、送信成功`eof_ps=e`、受信先の観測`observed_ps=o`、受信処理完了`received_ps=r`。未到達点はnull。予定時刻はplannedフィールドへ分離する。 |
| 識別 | `target`は完全インスタンスパス（キューは所有ノードパス+`.txQueue`）、全体集計だけは予約名`$all`。`request_id`はCAN負荷仕様の`<generator_id>:<ordinal>`。generator_idは実行内一意な`[A-Za-z_][A-Za-z0-9_]*`、ordinalは0始まりの生成連番。`receiver`は配送先完全パス。run_idは実行の識別として別フィールドに保持する。 |
| 送信待ち | `tx_wait_ps=s-g`は処理・キュー待ちを含む。`arbitration_wait_ps=s-q`は受理後のFIFO・バス・仲裁待ちを含む。両方SOF時に一回記録。仲裁敗北だけを再送と数えない。 |
| 転送・配送遅延 | `transfer_ps=e-s`をEOFで一回、`delivery_ps=r-g`を受信完了時に受信先ごとに一回記録。フィルタ不一致・未完了は標本除外とする。 |
| キュー量 | 待機要求数。ローカル候補を含み送信中を除く。H>0で時刻0の初期値と、受理・SOF・破棄の判定後の値を記録。満杯破棄でも同値の記録を残す。同時刻はイベント連番で識別する。 |
| 要求最終状態 | `processing`（送信処理中）、`pending`（受理済・未SOF）、`in_flight`（SOF済・未EOF）、`success`（EOF済）、`dropped`（満杯のdrop-newest）の排他的5状態。実行停止で未完了を破棄・送信失敗へ書き換えない。 |
| 受信最終状態 | 送信元を除く各接続先に`pending`（EOF後の伝搬/受信処理が未完了）、`received`、`filtered`を記録。受信行の作成契機はEOF到達とする。フィルタ不一致は観測時刻oで終端とし、受信フィルタ結果として独立集計する。 |
| 保存則 | `generated = processing + admitted + dropped`、`admitted = pending + in_flight + success`、`unfinished = processing + pending + in_flight`。送信試行`attempts=in_flight+success`、`retries=0`、`failed=0`（理想モデル）。一要求が多数受信してもsuccessは1。受信機会数`receiver_opportunities=received+filtered+rx_pending`は別集計。 |
| 未生成 | generatedの計数対象は終了境界未満に実際に生成した要求とする（異常時は境界時刻でも成功コミット済なら含む）。途中結果は最後にコミットしたイベントまでの状態を出力する。 |

## 2. 窓・指標・集計

<a id="aggregation"></a>

```trace
{
  "id": "spec-results#aggregation",
  "stage": "spec",
  "requirements": [
    "DIR-REQ-0043",
    "DIR-REQ-0085",
    "DIR-REQ-0086",
    "DIR-REQ-0088",
    "DIR-REQ-0089",
    "DIR-REQ-0090",
    "DIR-REQ-0091",
    "DIR-REQ-0115",
    "DIR-REQ-0120",
    "DIR-REQ-0008"
  ],
  "upstream": [
    "DIR-FUNC-0018",
    "DIR-FUNC-0019",
    "DIR-FUNC-0013"
  ],
  "state": "confirmed",
  "pending": []
}
```

| 規則 | 契約 |
| --- | --- |
| 全体区間 | `[0,H)`。正常時は早期イベント枯渇でもH=T。最後のイベント以降は定常状態をTまで積分する。注：この積分区間の延長は処理イベント数の計数対象外。last_event_time_psを別に記録する。異常時は診断仕様の部分prefix規則に従う。時間打切りでも正常終了であり、未完了件数を残す。 |
| 観測窓 | 幅W=`metrics-window`（ps、正値、既定1ms）。窓は`[kW,min((k+1)W,H))`。最終短縮窓にもその実長を使う。W>Hなら一窓、H=0なら窓なし。窓の境界は計測集計器が論理的に区切る。注：監視窓だけを目的とした実行イベント予約は対象外。 |
| 算術平均 | tx_wait / arbitration_wait / transfer / delivery各々について完了した観測点の標本だけを重み1で集計。deliveryは（要求,受信先）を一標本とし、全体平均では受信数の多い要求が標本数分寄与する。各受信先平均も出す。未完了は母数から除外し別件数を必ず出す。 |
| 時間加重平均 | `queue_mean = integral Q(t)dt / H`。イベント処理後のQを次の時刻まで保持し同時刻間隔は0。`queue_max`は初期値と全遷移後の最大を取り、ゼロ時間だけのピークも含む。 |
| 使用率 | `bus_utilization = measure(union [SOF,release) intersect window) / window_length`。intermissionを含む。`frame_utilization`は同じ式の区間を`[SOF,EOF)`としてintermissionを除く。終了時に未完了でも開始済区間をHまでクリップし、予定EOF以降を実行済と扱わない。 |
| バッファ使用率 | 容量Cのキューで`buffer_utilization=Q/C`をqueue_lengthと同じ各観測点に記録。窓平均と全体平均`buffer_utilization_mean=integral Q(t)dt/(C*interval_length)`も記録し、単位は`1`。C=0なら点・平均ともnull、区間長0の平均はnull。Q=0かつC>0なら0。容量は確定設定で参照可能とする。 |
| ペイロード量 | `payload_bits`はEOFで完了した各バス送信の8×データbyte数を一回加算。受信先別`received_payload_bits`はrで一回加算。バス量と受信先量は独立集計とする。 |
| 総転送量 | `serialized_bits`はEOFで完了したフレームのCRC・stuff・ACK・EOFを含むフレームbitsを一回加算（intermission除外）。`occupied_bits`はバス解放で完了したフレームbits+3を加算。完了量の集計対象は対応する完了点へ到達したフレームに限定し、部分占有は使用率に反映する。 |
| スループット | 各窓で`payload_throughput_bps=payload_bits*10^12/window_length`、`serialized_throughput_bps=serialized_bits*10^12/window_length`、受信先別`received_throughput_bps=received_payload_bits*10^12/window_length`。完了点で窓に帰属し、途中フレームは完了点を含む窓へ全量を帰属させる。全体値は総量/全長であり窓の単純平均ではない。 |
| 破棄 | `dropped`は対象キュー・原因`queue_full`別に集計。注：フィルタ不一致、仲裁敗北、未完了、処理失敗は破棄集計の対象外。 |
| 空集合・ゼロ | 標本数0の平均はnull。H=0の比率・時間加重平均はnull、正常H=0の件数・量は0、初期空キュー最大は0。欠損の数値表現はnullとする。正長のアイドル窓は使用率0・スループット0。 |
| 算術 | 時刻はu64、件数・和・積分分子はchecked u128相当以上の正確整数で保持し、あふれはE-0004。平均・率だけを有理数からbinary64最近接偶数丸めへ一度変換。有限でなければE-0004。集計順はイベント順で固定。 |
| 部分prefixの窓 | 異常時Hにある成功コミット済の点記録はrecordsとsummaryへ含め、[0,H)の窓集計から除く。窓は全て正長半開区間のままとし、H=0でも成功点記録が存在し得る。summaryの完了量/標本数と窓の総和の差はHの成功点だけに一致する。H以前のコミットで開始した使用率区間はHまで積分する。 |
| 拡張 | 指標登録は`metric_id/version/unit/value_kind/sampling/aggregation`を必須とし名前重複を準備失敗とする。既存指標の意味変更はmetric versionとschema_versionを更新。初期版は下表に列挙した指標のみ登録し、注：利用者の任意式評価は提供範囲外。 |

| 指標ID | unit | value_kind | 出力範囲 |
| --- | --- | --- | --- |
| `queue_length`, `queue_max`, `generated`, `admitted`, `processing`, `pending`, `in_flight`, `success`, `dropped`, `unfinished`, `attempts`, `retries`, `failed`, `receiver_opportunities`, `received`, `filtered`, `rx_pending` | `count` | integer | queue_lengthは点標本、queue_maxはキュー別全体集計、件数は下表の対象別/全体集計 |
| `tx_wait_ps`, `arbitration_wait_ps`, `transfer_ps`, `delivery_ps` | `ps` | integer | 個別イベント標本 |
| `tx_wait_mean_ps`, `arbitration_wait_mean_ps`, `transfer_mean_ps`, `delivery_mean_ps` | `ps` | number | 各対象と全体の標本平均 |
| `queue_mean` | `count` | number | キューごとの全体集計 |
| `buffer_utilization`, `buffer_utilization_mean` | `1` | number | キューごとの点標本、観測窓平均と全体平均 |
| `bus_utilization`, `frame_utilization` | `1` | number | バス別観測窓と全体集計 |
| `payload_bits`, `serialized_bits`, `occupied_bits`, `received_payload_bits` | `bit` | integer | バスまたは受信先別観測窓と全体集計 |
| `payload_throughput_bps`, `serialized_throughput_bps`, `received_throughput_bps` | `bit/s` | number | バスまたは受信先別観測窓と全体集計 |

| 出力集合・対象 | 必須行と集計規則 |
| --- | --- |
| 点記録 | queue_lengthとbuffer_utilizationはtarget=キュー完全パス、tx_wait_ps/arbitration_wait_psは送信元、transfer_psはバス、delivery_psは受信先。要求起因はrequest_idを設定し、deliveryのみreceiverも設定する。初期キュー記録のrequest_idはnull。reasonは全てnull。 |
| 件数summary | generated/admitted/processing/pending/in_flight/success/unfinished/attempts/retries/failedは各送信元、各バス、予約対象名`$all`へ要求を一度ずつ集計。droppedも同じ対象にreason=queue_fullで出し、各キューにもその破棄数を出す。0件でも行を出す。他の件数のreasonはnull。 |
| 受信summary | receiver_opportunities/received/filtered/rx_pendingは各受信先、各バス、`$all`へ（要求,受信先）を一度ずつ集計。受信先行のreceiverはその完全パス、バス/$allはnull。送信対象にもなるノードでは要求件数と受信件数を独立に保持する。 |
| 遅延summary | tx_wait_mean_ps/arbitration_wait_mean_psは各送信元・各バス・$all、transfer_mean_psは各バス・$all、delivery_mean_psは各受信先・各バス・$all。標本数をsample_countへ、受信先別deliveryではreceiverにも完全パスを設定。他はreceiver=null。注：遅延の窓平均は初期出力の対象外。 |
| 窓とsummary | bus_utilization/frame_utilization/payload_bits/serialized_bits/occupied_bits/payload_throughput_bps/serialized_throughput_bpsは各バス。received_payload_bits/received_throughput_bpsは各受信先（receiverにも同じパス）。buffer_utilization_meanは各キュー。それぞれrecordsへ全窓の行、summaryへ[0,H)の一行を出す。queue_mean/queue_maxは各キューのsummaryのみ。対象は接続済モデルから作成し0件でも全て出力する。 |
| 補助列 | 集計行のrequest_idはnull、上記で指定したもの以外のreceiver/reasonはnull。sample_countは算術標本平均だけに使い、時間加重平均・使用率・スループットはnullとする。全体summaryのstart_ps=0、end_ps=H。 |
| 保持値と最大 | queue_maxは初期値とHより前の全変化後の値を含む（異常prefixはHの成功変化も含む）。満杯で値不変の点も出力する。queue_meanの分子は同時刻の最後の確定値を次時刻まで保持して積分する。 |
| メトリクス登録値 | versionは文字列`1`。samplingは点指標=`point`、件数/queue_max/queue_mean/遅延平均=`summary`、それ以外=`window_summary`。aggregationは点=`identity`、件数とbit量=`sum`（状態件数は終端台帳上の該当要素数）、queue_max=`max`、遅延平均=`sample_mean`、queue_meanとbuffer_utilization_mean=`time_mean`、使用率=`occupancy_ratio`、スループット=`rate`。 |


| 共通項目 | 確定スキーマ |
| --- | --- |
| 型略記 | Dは先頭0なしの非負10進数字文字列（0のみ例外、時刻/イベント予約sequenceはu64、件数/量/記録連番はu128以内）、SはUTF-8文字列、Nは有限JSON number、?はnull可、配列は`[]`で示す。全フィールド必須、任意値もキーを保持しnullで表す。schema_versionはJSON整数1。 |
| エンコーディング | UTF-8 BOMなし。JSON objectはキーのUTF-8辞書順、compact表現、末尾LF。integer値・全時刻・件数はD、率・平均はN?。CSVはheaderあり、カンマ区切り、LF、引用符/カンマ/改行を含むセルを二重引用符で囲み内部引用符を二重化。CSVのnullは空セル、numberはJSONと同じ有限十進表記。 |
| 文字と数値のwire表現 | JSON文字列はUnicode正規化を行わず、quoteとbackslashをエスケープしU+0000～001Fを小文字hexの`\u00xx`で表す。他のUnicode scalarはUTF-8をそのまま保存しslashをエスケープしない。Nはbinary64を十進有効17桁へ最近接偶数丸めし、`d.dddddddddddddddde±n`形式（小数部16桁、指数の先頭0なし）で出す。0は`0.0000000000000000e+0`、負0は正0へ正規化。CSVも同じ文字列を使う。以下のJSON例は説明用のキー順/短いNを許す表示例であり、ファイル保存時はこの正規表現に従う。 |
| ファイル集合 | `manifest.json`, `results.json`, `events.csv`, `summary.csv`, `diagnostics.jsonl`の5ファイル。CSVはresults.json内のrecords/summaryと一対一で復元可能。要求台帳・メタデータはresults.jsonを参照する。 |
| results.json | `{schema_version:1,run_id:S,metadata:Metadata,simulation:Simulation}`。Simulation=`{termination:S,partial:boolean,start_ps:D,end_ps:D,last_event_time_ps:D?,committed_events:D,pending_events:D,records:Record[],summary:Record[],requests:Request[],receivers:Receiver[]}`。start_psは0、end_psはH。terminationは診断仕様のtime_limit/events_exhausted/prep_failed/execution_failedで、保存失敗のoutput_failedは公開済simulationへ設定する値ではない。 |
| Record（列順も固定） | `{seq:D,event_seq:D?,effect_seq:D?,target:S,metric:S,unit:S,value_kind:S,value:DまたはNまたはnull,time_ps:D?,start_ps:D?,end_ps:D?,request_id:S?,receiver:S?,reason:S?,sample_count:D?}`。integerならvalue=D、numberならN?。点標本はtimeのみ、窓/全体集計はstart/endのみを非null。算術標本平均にはsample_count、他はnull。metric versionは初期版すべて1でmetadataに登録。 |
| CSV列 | `schema_version,run_id,seq,event_seq,effect_seq,target,metric,unit,value_kind,value,time_ps,start_ps,end_ps,request_id,receiver,reason,sample_count`。events.csvはrecords、summary.csvはsummaryを同じ順序で射影しschema_version/run_idを付ける。 |
| Request | `{request_id:S,source:S,bus:S,status:S,generated_ps:D,ready_ps:D?,sof_ps:D?,eof_ps:D?,payload_bits:D,serialized_bits:D?,model_fields:CanFields,attempts:D,retries:D,drop_reason:S?}`。到達したreadyは満杯破棄にも記録。初期CANはprepareでフレーム長を計算済みとし、生成成功時からserialized_bitsとmodel_fieldsを設定する。nullableなserialized_bitsは将来モデルの共通欄であり初期CANは常にD。 |
| CanFields | `{profile:S,schema_version:1,crc15:D,stuff_bits:D,frame_bits:D,intermission_bits:D,bitrate_bps:D,planned_eof_ps:D?,planned_release_ps:D?,release_ps:D?}`。profileは`can.cc.ideal.v1`、crc15は0～32767、intermission_bitsは`3`、frame_bitsはserialized_bitsと一致。SOF前の予定時刻はnull、予定時刻はSOF時に設定、release_psはバス解放到達時だけ設定。初期CANのコミット済Requestは生成時から全内訳を保持する。 |
| Receiver | `{request_id:S,receiver:S,status:S,observed_ps:D?,received_ps:D?}`。受信先のpendingには観測前と観測後の受信処理中を含み、到達時刻で区別する。 |
| 安定順序 | recordsを有効時刻（点はtime_ps、窓はend_ps）、同時刻の窓→初期点→callback点の種別順、callback実行コミット順、effect_seqの順に並べる。窓内と初期点はtarget/metric/reason/receiverのUTF-8辞書順。summaryも同じ辞書順。requestsはrequest_id順、receiversはrequest_id/receiver順（ordinalの数値順とは異なる）。nullは全ての文字列より前。seqはrecords/summary各配列で0から隙間なく採番する。 |
| 観測の出自 | event_seqはruntimeの予約sequence、effect_seqは一callbackが報告する観測だけを0始まりで数えた連番（予約等の他効果は計数対象外）。callback内の複数対象を一括報告する場合はtarget/metric/request_id/receiver順に展開して採番する。初期点と集計行は両方null。実行コミット順はruntimeの処理順であり、注：予約sequenceの数値sortは処理順の代用対象外。 |
| multibus schema2 | Request・ReceiverはModelRecordへ格納する。[GW仕様](models/GWモデル詳細機能仕様書.md#payload-results)でMultibusFields.tx_enqueued_ps（nullableな実TX受理時刻）、waiting_tx状態/summary、gw.rx_buffer/1とRX/TX待ち指標を定める。ready_psは初回TX処理完了のまま、arbitration_wait_psはSOF−tx_enqueued_ps、tx_wait_psはSOF−generated_ps。unfinishedとgenerated保存則へwaiting_txを加え、TX queue_lengthには含めない。本書のschema1 Request/CanFieldsと既存metric集合は保持する。 |
| model_fieldsの拡張 | model_fieldsはprofileとschema_versionで解釈するモデル別オブジェクト。初期版はCanFields（schema_version=1）を用い、将来モデルは独立したschemaを登録する。共通exporterはその識別と直列化済みオブジェクトを扱い、固有フィールドの意味はモデル側に属する。 |
| pending_events | 終端snapshotに残る有効な実イベント数、まだphase 2予約へ実体化していないdirty資源数、dispatcherの次回予約を遅延展開している場合の論理予約1件の合計。dirtyは(time,delta,resource)ごとに一件と数え、実体化済み予約との二重算入は除外する。取り消し済みイベントは除外。失敗候補は有効集合から成功コミット時にだけ消費するため異常snapshotにはその候補も含む。将来生成が存在するdispatcher予約が既に実イベントに含まれる場合は一度だけ計数する。注：未生成の全要求数やgeneratorの総発火回数は計数対象外。 |
| manifest.json | `{schema_version:1,run_id:S,status:S,termination:S,partial:boolean,metadata_ref:S,files:File[]}`。File=`{name:S,sha256:S,bytes:D}`。metadata_refは`results.json#/metadata`固定で、実験メタデータの唯一の正本を参照する。自身を除く4ファイルをname順に列挙。statusは`complete`のみ（5ファイルの公開成功を示しシミュレーションの成功とは別）。SHA256は完成ファイルraw bytesの64桁小文字hex。 |
| diagnostics.jsonl | 診断詳細仕様のDiagnostic objectを一行一件。正常時は空ファイル。 |
| exporter拡張 | exporter登録を`format_id/schema_version/export(snapshot)`で分離する。既存の5ファイル契約は必須。追加形式は別名ファイルとmanifest項目を追加するschemaの新versionで提供し、既存形式の列と意味を保持する。 |
| 台帳整合性 | Requestのstatusがprocessingならready/sof/eof=null、pendingならreadyのみ、in_flightならready/sof、successならready/sof/eofが非null。droppedはready非null、sof/eof=null、drop_reason=queue_full。他状態のdrop_reasonはnull。planned_eof/planned_releaseはSOF前ともにnull、SOF後は両方設定されeの実到達とは分離する。時刻はg≤q≤s≤e、attemptsはSOF前0/後1、retries=0。ReceiverはEOF済要求だけを参照し、pendingはreceived=null、filteredはobserved非null/received=null、receivedは両方非nullかつe≤o≤r。release_psが非nullならe≤release。参照先要求/インスタンスは実行内に存在し台帳キーは一意とする。 |
| 読み戻し | 未対応schema_version、不正D、非有限値、重複seq、対象型とunit/value_kindの不一致、manifest hash不一致は不正出力として拒否する。利用者がCSVのみを読む場合もrun_idとschema_versionでJSON/manifestへ対応付ける。 |

## 4. メタデータ・再現条件

[実験条件と結果の対応](../要件定義書.md#dir-req-0117)は、入力snapshot・確定値・モデル前提をこの実行の結果へ結び付ける責務である。[再現性](../要件定義書.md#dir-req-0045)の確認は、それらの条件をそろえて再実行し、本書の比較範囲に従って`simulation`を照合する。メタデータの保存、イベント順の決定性、モデル計算と集計の一致を組み合わせて確認し、実時間やrun_idの差は実行の識別情報として扱う。

| `config` | `{key:S,value:S}[]`。型解決済の全設定をkey/valueのSペア配列に正規化しkey順に保存（単位はps/bit/s/byte/count、文字列はJSON引用、真偽はtrue/false）。default由来の値も含める。 |
| `config_sha256` | S。configのcompact canonical JSON UTF-8（末尾LFなし）のSHA256。 |
| `input_sha256` | S。sourcesのlogical_pathとsha256だけをキー順compact JSON化した配列（末尾LFなし）のSHA256。注：絶対パス・実時間はhash入力対象外。 |
| `runtime_version`, `git_commit`, `binary_sha256`, `model_registry_version`, `compiler`, `target_triple`, `os`, `cpu` | S。実行器の版、完全Git commit、実行バイナリraw SHA256、モデル登録版、rustcの完全版、ビルドtarget、OS名/版、CPUアーキテクチャ/モデル。不明は空文字ではなく`unknown`を明記し再現条件未同定として扱う。 |
| `cargo_lock_sha256`, `toolchain`, `adoption_ledger_version` | S。実行バイナリ構築に使ったCargo.lock raw bytesのSHA256、`rustc -Vv`の完全出力、採用モデル/外部仕様台帳の版または完全Git commit。未取得は`unknown`とし再現条件未同定と明記する。compilerは短い版識別、toolchainは詳細の正本。 |
| `models` | `{type:S,version:S,assumptions:S[]}[]`。type順。初期CANは`can.cc.ideal.v1`、理想ACK・再送なし・エラー注入なし・フレーム単位内容依存時間・固定伝搬遅延・送信元自己配送なし・フィルタとACK独立を列挙。 |
| 準備失敗のmetadata | 型を変えず、取得完了済sourcesのみ保存し、configは値解決全件成功前なら空配列、initial_stateは初期化全件成功前なら空配列とする。modelsは照合済登録、metricsは組込み全登録を保存。window_psは解決前なら既定値1000000000、解決後なら確定値。空config/sourcesにも通常のhash計算を適用する。未取得の版/環境値はunknownとし、入力のraw内容が取得できてもUTF-8不正ならsources要素を追加しない。 |
| `topology` | schema1/2共通のController接続情報。controllersは`{id:S,bus:S,tx_channel_delay_ps:D,rx_channel_delay_ps:D}[]`をid順に保存する。準備済みのBus所属とTX/RX経路遅延を正本とし、通信のないControllerも含む。構成図はこの所属を参照する。 |
| `initial_state` | `{instance:S,state:S}[]`をinstance順。各モデルversionで定義された初期状態のcanonical JSON文字列（CANの具体形はCAN仕様の初期状態表を正本とする）。キュー空・バスidle・生成連番0・設定で確定した生成列を識別できる状態を含む。 |

| `time_resolution_ps`, `window_ps`, `seed` | D、D、S?。time_resolution_ps=`1`、window_ps=解決済W、既存の乱数未使用profileはseed=null。Ethernet v2のbackoffは媒体仕様のseedを正規十進文字列として保存。 |
| `run_id`（外側） | 各実行開始時のUUIDv4文字列。別実行で必ず新規採番。結果の同一性はmetadataやrun_idではなくsimulationを比較する。CSV比較ではrun_id列を除く。 |
| 再現保証 | 同一入力内容・論理配置・確定値・初期状態・runtime/model/metric版と同一実行環境でsimulationのイベント順と値が一致。異なる計算機については固定版の整数時間/決定的順序/丸めに従うsimulationだけを比較対象とし、注：実時間・OS/CPU・パス・run_id・バイナリhashの一致、および未同定版や異なる版での同一結果は保証範囲外。 |

| モデル固有 | GWの元要求／転送copy、AXItransaction／handshake／RAM、Ethernetframe／hop／receptionを独立schemaとして保存。Ethernet v2は試行・衝突・backoff・PHY状態を登録されたschema版で追加する |
| 指標集合 | 37指標の一律生成は既定CANに限定。追加profileはそのspecに列挙したmetricをmetadataへ登録して計測する |
| 再現情報 | model-configもsourcesへ保持。Metadata2はmodel_profileとmodel_schemasを追加し、unknown値と準備失敗時の扱いは本書を継承 |

## 将来対応モデルへの適用

現行Classical CANのschema1と指標集合を維持し、以下の将来モデルは[schema2](拡張モデル共通詳細機能仕様書.md#results)の登録レコードとモデル別の母数を使用する。仕様の存在と製品実行試験の完了は別に扱う。

| 項目 | 契約 |
| --- | --- |
| 将来モデル | 追加モデルの要求、段階別時刻、内容・所有権、未完了と破棄理由を登録ModelRecordへ保存する。CAN固有指標はCAN profileに適用し、各追加モデルの指標は専用descriptorを登録する。停止時は成功commit prefixから出力する。 |
| 正本 | [CAN FD・100BASE-T1](models/CANFD・100BASE-T1詳細機能仕様書.md)、[SoC・AHB・NoC](models/SoC・AHB・NoC詳細機能仕様書.md)、[DDR・SRAM・共有メモリIPC・DMA・メールボックスIPC](models/メモリ・IPC詳細機能仕様書.md) |
