## 1. 対象と管理元

機能に関する要件は、要件定義書 → 機能仕様書 → 詳細機能仕様書 → アーキテクチャ設計書 → 詳細設計書 → 検証仕様書の全工程を追跡する。
[ドキュメント作成・運用規約](ドキュメント作成・運用規約.md#23-要件から詳細仕様設計検証への追跡)に従い、責務の対応は多対多で扱う。文書そのもののリンクだけでなく、担当する規則・要素・設計上の確認対象・検証ケースを識別する。

| 情報 | 正とする箇所 |
| --- | --- |
| 要件本文・例外経路 | [要件定義書](要件定義書.md) |
| 主親・掲載順・階層上の位置・分解状態 | [要件階層.json](要件階層.json)。本文と同じ掲載順とし、閲覧用HTMLは生成する |
| 機能本文・要件から必要な機能への割当 | [機能仕様書](機能仕様書.md)の各機能と第11.2節 |
| 機能以降の工程間の割当 | 下流項目の本文に置く `trace` 記録 |
| 期待結果・検証手順・実行証跡 | 検証仕様書のケース本文。ACは受け入れ条件の管理元 |
| 逆引き・全体経路 | 上記の記録から算出する。手作業で別の全体対応表を保守しない |

必要な内容を複数項目で分担するときは、全項目を登録する。一件の検証へたどり着けることだけでは、ほかの分担の欠落を埋められない。
同じ機能が複数要件を担う場合、要件Aのための仕様・検証を要件Bの証拠と混同しないよう、項目ごとに対象要件を明示する。

## 2. 項目の識別と記録形式

要件は `DIR-REQ-NNNN`、機能は `DIR-FUNC-NNNN` を使う。詳細仕様・アーキテクチャ・詳細設計の項目は **文書ID#明示アンカー** で識別する。文書IDとアンカーは一意で安定した英小文字・数字・ハイフンを用い、番号・見出し・表示名・配置を変更しても同じ責務なら維持する。
検証ケースは `DIR-TEST-NNNN` とし、定義の直前に `<a id="dir-test-NNNN"></a>` を置く。番号は全検証仕様で一意に採番する。廃止したID・アンカーは再利用しない。

各項目の明示アンカーと本文の近くに、言語名を `trace` とするJSONコードブロックを一つ置く。一つの文書に複数項目を記載できる。文書IDだけを登録して、複数の規則・不変条件を追跡対象から隠さない。
以下は書式例であり、実際の割当・仕様確定を示さない。通常の `json` ブロックは検査の登録対象にしない。

```json
{
  "id": "spec-configuration#instance-override",
  "stage": "spec",
  "requirements": ["DIR-REQ-0025"],
  "upstream": ["DIR-FUNC-0008"],
  "state": "draft",
  "pending": ["重複指定を含む受理入力の契約が未確定（DIR-TBD-0003）"]
}
```

| 項目 | 必須の内容 |
| --- | --- |
| `id` | この項目の安定したID。検証以外は冒頭の文書IDと実在する明示アンカーを組み合わせる |
| `stage` | 下表の工程。文書名だけから推測しない |
| `requirements` | 担当する有効要件IDの非空配列。範囲表記や親からの暗黙継承を使わず列挙する |
| `upstream` | 直前の工程の項目IDの配列。複数ある場合は全担当元を列挙する |
| `state` | `draft` または `confirmed`。項目の内容の確定状態であり、試験結果ではない |
| `pending` | 未作成工程・未確定の規則・未割当の分担など、経路を完了扱いにできない理由の配列。残課題がない場合は空配列 |

| `stage` | 文書・対象 | 必須の直前工程 |
| --- | --- | --- |
| `spec` | 詳細機能仕様の個別規則 | 機能ID |
| `architecture` | アーキテクチャの構成要素・責務 | 詳細機能仕様の項目ID |
| `design` | 詳細設計の処理・データ・不変条件等の確認単位 | アーキテクチャ要素ID |
| `verification` | 試験・レビューのケースID | 詳細設計の項目ID。第3章の例外のみ要件IDを直接参照可能 |

上流項目への本文リンク、どの責務を担当するか、複数の分担が共同で満たす条件も記す。先行工程を飛ばした補助リンクは根拠参照として併記できるが、必須の隣接工程を置き換えない。
各対象要件には、その要件を担当する上流が必要である。上流Aが要件X、上流Bが要件Yを担当する項目では、それぞれの要件の経路だけを検査する。対象範囲を広く列挙するだけで割当済みとはしない。

未作成の上流は架空のIDで参照せず、`upstream: []` と非空の `pending` で未割当を記録する。上流が存在してもその要件の経路がなければ割当漏れとして検出する。存在しないIDへの参照は記載ミスとして修正する。
下流が未作成の項目は、下流記録がないことから未完了として検出する。詳細仕様・アーキテクチャ・詳細設計は終点にしない。`confirmed` に未解消の `pending` を残してはならない。
`draft` でも対応の構造は点検できる。構造が完備していることと、内容の確定・十分性は別にレビューする。

## 3. 制約の代替経路

機能の振る舞いでは確認できない制約は、要件定義書に `trace-exception` ブロックを置く。現在の代替経路は **要件 → 検証仕様のレビューケース** のみとする。出自・実装・公開インタフェース等の確認資料はケース本文で参照する。

```json
{
  "requirement": "DIR-REQ-0047",
  "reason": "実装言語は対象ソースとビルド構成のレビューで確認するため",
  "stages": ["requirement", "verification"]
}
```

例外登録は要件ごとに一件とし、対象と理由を明記する。検証ケースが作られるまで未完了である。全要件対応表の機能欄は制約の適用先として維持するが、例外の充足経路には数えない。
例外を追加・変更するときは省略が適切かレビューする。未作成・工数・実装の都合を理由に例外化しない。機能を持つ要件や再現性要件を自動的に例外へ分類しない。

## 4. 検証ケースと変更影響

ケース本文には対象の設計項目ID・詳細機能仕様の規則・要件ID・機能ID・AC、確認方法、入力、独立した期待結果、判定基準、実行結果への参照を記す。
機能の外から確認するケースも担当する設計責務を特定する。内部の不変条件・エラー伝播・資源解放等は必要な試験またはレビューを別途割り当て、外部出力の確認だけで検証済みとしない。
例外のレビューケースは省略工程を非該当と記載し、例外理由と根拠資料を参照する。

変更時は項目IDから上流・下流をたどり、根拠要件、影響する仕様・構成要素・設計、再検証するケースを確認する。分担が複数あれば一枝で打ち切らない。
上流へ戻った結果ほかの分担にも影響する場合は、それらの項目から再度下流を確認する。逆引きは影響調査の候補であり、意味上の影響の有無はレビューで判断する。
同じ文書IDのままファイルを移動・改名する場合や文書内で項目を移動する場合は、識別子を維持し、パスと本文リンクを更新する。項目を別の文書IDへ移す場合は、新しい文書IDとアンカーで採番し、旧IDと後継IDの対応および移動理由を本文に残して、現行の参照を更新する。責務の分割・統合・廃止も旧項目の理由と後継を残す。過去の割当はGitで追跡する。

## 5. 検査コマンドと完了条件

リポジトリのルートで実行する。スクリプトの絶対パスを指定すれば、別のディレクトリからも使用できる。

```bash
# 登録の整合性を検査し、未完了の経路を報告する
python3 scripts/check_traceability.py

# 全要件の全経路が検証仕様までつながっていることを要求する
python3 scripts/check_traceability.py --strict

# 実装へ進む対象要件を限定して検査する（複数指定可能）
python3 scripts/check_traceability.py --strict --requirement DIR-REQ-0025

# 変更する項目の上流根拠と下流影響を調べる
python3 scripts/check_traceability.py --impact DIR-FUNC-0008
python3 scripts/check_traceability.py --impact 'architecture#arch-parameters'
```

### 5.1. 横方向一覧の経路表示

全有効要件から検証までの一覧は、[Markdown版](要件トレーサビリティ一覧.md)と[HTML版](要件トレーサビリティ一覧.html)を同じ正本データから生成する。Markdown版は要約とHTML形式の横方向表を含み、HTML版は単独で開けるスタイル付きレポートである。どちらも手編集せず、詳細な意味と項目本文はリンク先のMarkdown文書を正とする。

通常経路の列は **要件 → 機能 → 詳細機能仕様 → アーキテクチャ → 詳細設計 → 検証** とし、一行を実際に登録された完備経路または未完了経路一つに対応させる。各工程セルには、その経路を構成するIDを一件だけ本文へのリンク付きで表示する。異なる要件の経路で同じ下流IDを使う場合も各行・各セルに繰り返し表示し、同じ正規のリンク先を使う。受け入れ条件（AC）は機能や設計の工程として挿入せず、要件とACを対応させる独立した表に表示する。

行は要件ID・機能IDの組合せだけで作らず、正本に明記された隣接工程間の辺を要件スコープごとにたどって作る。共通要件への所属や `requirements` の列挙だけを接続根拠にしない。要件から機能への対応は機能仕様書の明示的な割当、以降は正しい要件スコープを持つ `upstream` を接続根拠とする。分岐を含む全ての完備・未完了経路を末端まで表示する。隣接行のセルを `rowspan` でまとめる場合は、同一要件・同一経路種別（通常経路、未接続断片、登録例外経路、適用先の参考経路）の連続行に限り、そのセルまでの上流ID列が同じ場合に共有する上流セルだけをまとめる。要件や経路種別をまたいで同じIDをまとめない。

有効な辺から要件まで到達できない登録項目・分岐、未割当または孤立した機能、無効・未割当の要件項目は、通常の経路行へ混ぜず、区別した行グループ・項目一覧または構造診断として全件表示する。孤立した項目に対象要件が宣言されていても、上流辺がなければ要件からの経路とはみなさない。登録ノードや有効な辺をレポートから黙って除外せず、構造診断も省略しない。

診断では、直前工程への割当がない「上流未割当・上流未接続」、次工程への割当がない「下流未割当」、前段から経路をたどれない「未到達」、参照先が登録されていない「不明ID」を区別する。不明IDなどの構造エラーは該当IDと参照元を表示する。例外経路は要件定義書に登録された場合に限り、対象外工程を「非該当（登録例外）」と明記して表示する。例外要件に機能IDの割当があっても、それは適用先の記録であり、要件から検証までの通常経路を構成しない。例外が成立するのは登録された要件から検証ケースへの経路だけである。 適用先の機能から仕様以降への対応も明示されている場合は参考経路として表示し、例外の充足経路とは区別する。適用先に仕様への割当がないことだけでは例外経路の欠落としない。

接続完了・未完了・例外・構造エラーは記号だけでなく文字でも表示する。工程ごとに淡色の背景を使い、欠落は黄色、構造エラーは赤系で示す。GitHubのMarkdown表示は埋込みHTMLのCSSを除去することがあるため、背景色を確実に確認する場合は生成HTML版をローカルのブラウザーで開く。色を認識できなくても診断名と文字ラベルで状態を判別できるようにする。一覧は全件を表示し、任意の件数で切り捨てない。

一覧の「文書と対象バージョン」には、`docs/`配下のテンプレート・一覧自身を除くMarkdown文書の正式名、文書バージョン、対象GitHubバージョンを各文書の冒頭から転記する。必要な値が未記載の場合は一覧にも「未記載」と表示する。文書バージョンの収録は既存の文書版管理規則に従い、一覧自身には独立した文書バージョンを設けない。

```bash
# 一覧2形式と要件階層の別紙HTMLを生成・更新する
python3 scripts/generate_traceability.py

# 3ファイルが最新か、階層データが整合しているか確認する
python3 scripts/generate_traceability.py --check

# --root でリポジトリを指定し、3ファイルを生成または確認する
python3 /path/to/DIR-Simulator/scripts/generate_traceability.py --root /path/to/DIR-Simulator
python3 /path/to/DIR-Simulator/scripts/generate_traceability.py --root /path/to/DIR-Simulator --check

# このクローンでコミット時の自動更新を有効にする（初回のみ）
git config core.hooksPath .githooks
```

| 文書版と一覧の更新 | 運用 |
| --- | --- |
| 文書版と一覧の順序 | [文書版のpush時更新](ドキュメント作成・運用規約.md#document-version-at-push)に従い、push実施者が送信範囲の変更を文書ごとに一改訂へまとめ、版番号と履歴を確定してステージし、その後に一覧を生成してコミット・pushする。通常の編集・ローカルコミットでは版番号を維持し、一覧はその時点の文書ヘッダーから生成する |

pre-commit hookは、トレーサビリティ一覧の2形式・要件階層HTMLのいずれか、階層の編集元 `docs/要件階層.json`、`scripts/check_traceability.py`、`scripts/generate_traceability.py`、`scripts/requirement_hierarchy.py`、あるいは `docs/` 配下のテンプレート以外のMarkdown文書がステージされている場合に実行する。ステージ済みファイルのスナップショットから一覧2形式と要件階層HTMLを生成し、生成した3ファイルをステージへ追加する。階層データの欠落・重複・不明親・循環もコミット前に検査する。追跡データに構造エラーがある場合はコミットを止める。未完了の経路は一覧に文字ラベル付きで残し、厳格検査の合格をコミット条件にはしない。

通常検査はID・アンカー・文書ID・要件スコープ・参照先・工程順等の不正を失敗とし、明示した未完了を報告する。通常検査の成功を「全工程の追跡完備」と呼ばない。
厳格検査は対象要件の全分担について、6工程または登録例外経路、各要件の上流根拠、未解消の `pending` がないこと、末端が検証ケースであることを要求する。途中で終わる枝が一本でもあれば失敗する。
要件を限定しても、存在しないID・不正な登録など全体の整合性検査は省略しない。親要件を扱う際は必要な子要件も検査対象へ含め、親本文の網羅・統合検証をレビューする。親子の意味上の充足を自動計算しない。

`specs/`、`design/`、`verification/cases/` の本文文書には最低一つの登録が必要である。テンプレート、記述例、履歴資料を実際の仕様項目として登録しない。検証計画書そのものはケースではない。
機械検査に加え、各文書内のすべての規則・設計義務が適切な粒度で登録されているか、対応が意味上十分か、正常・境界・異常時が覆われているかをレビューする。検査の合格は実装済み・試験合格を意味しない。
