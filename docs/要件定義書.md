## 1. 目的

ネットワークおよびSoC内部の通信・共有資源を、共通の離散イベントシミュレーションで評価できるようにする。
通信や資源利用に伴う遅延、競合、バッファ使用状況を再現し、性能指標を取得できることを目的とする。

### 1.1. 想定する利用とシステム境界

利用者はネットワーク・SoCの評価モデルを作成し、同じ構造に対して処理遅延、帯域、バッファ容量などの条件を変え、結果を比較する。
モデル開発者はRustで振る舞いを実装し、NEDで宣言した型と対応付ける。

入力はNEDによる構造定義、INIによる実験条件、Rustの振る舞い実装であり、出力はシミュレーション結果と診断情報である。
利用インタフェース、実行環境、性能保証の範囲は `DIR-TBD-007`・`DIR-TBD-008` で管理する。

### 1.2. 本書に記載する内容

本書は、利用目的、対象・対象外、外部入出力、必要な振る舞い、品質・制約、検証条件、および未確定事項を記載する。
各要件は原則として一つの検証可能な責務を表し、上位の対象範囲は機能要件と受け入れ条件へ具体化する。
要件の主語は、特記しない限りDIR Simulatorとする。

入出力、値の解決、境界条件、異常時の具体的な振る舞いは[機能仕様書](機能仕様書.md)で扱う。未確定事項の管理元は本書の第6章とする。
追跡は[トレーサビリティ管理規約](トレーサビリティ管理規約.md)の6工程を適用し、第4.3節に登録した制約は理由付きの代替経路を用いる。
機能は `DIR-FUNC-NNN` で識別する。[機能仕様書の対応表](機能仕様書.md#11-要件機能受け入れ条件との対応)には全有効要件を一件一行で掲載し、各要件を満たすための機能の組み合わせ、機能定義の充足判断、不足・未確定事項、検証先を管理する。
trait、構造体、アルゴリズム、crate分割は[アーキテクチャ設計書](アーキテクチャ設計書.md)で扱う。
Rust、NED、INIの採用はプロジェクトで選択した制約として本書にも残す。
記述と点検にはNASAの[要件記述指針](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)と[技術要件の定義](https://www.nasa.gov/reference/4-2-technical-requirements-definition/)を参考にする。

## 2. 対象範囲

### 2.1. 対象システム

- <a id="dir-req-001"></a>**DIR-REQ-001**：外部ネットワークとして、CAN / CAN-FD、Ethernet（100BASE-T1 / 100BASE-TX）、ゲートウェイ、スイッチを扱えること。
- <a id="dir-req-002"></a>**DIR-REQ-002**：SoC内部通信として、SoCバス、AXI / AHB相当の内部通信、NoCを扱えること。
- <a id="dir-req-003"></a>**DIR-REQ-003**：メモリとして、DDR / SRAMを扱えること。
- <a id="dir-req-004"></a>**DIR-REQ-004**：IPC・データ転送として、共有メモリIPC、DMA、メールボックスIPCを扱えること。

これらの要件は評価対象の分野を定めるものであり、各規格の全機能や物理層の完全再現を保証するものではない。
再現する振る舞いと省略する振る舞いは `DIR-TBD-001` で分野ごとに確定する。

### 2.2. 提供する機能

システムの定義から結果の出力まで、次の流れを実行できること。

1. <a id="dir-req-005"></a>**DIR-REQ-005** **定義（Definition）**：NEDでシステムの構造、型、接続、デフォルトパラメータを記述する。
2. <a id="dir-req-006"></a>**DIR-REQ-006** **初期化（Initialization）**：INIでシナリオを指定し、インスタンスごとのパラメータを確定する。
3. <a id="dir-req-007"></a>**DIR-REQ-007** **実行（Runtime）**：Rustで実装した振る舞いを離散イベントとして実行する。
4. <a id="dir-req-008"></a>**DIR-REQ-008** **結果出力**：性能指標を記録し、CSVとJSONで出力する。

### 2.3. 対象外

| 対象外ID | 区分 | 対象外とする機能 |
| --- | --- | --- |
| `DIR-OOS-001` | NEDの型・名前解決 | モジュール継承、`import`、ワイルドカードによるインポート |
| `DIR-OOS-002` | NEDの構造展開 | 動的モジュール生成、条件付きサブモジュール、モジュールベクトル、ループによる接続生成、条件付き接続 |
| `DIR-OOS-003` | ゲート | `inout`、ゲートベクトル、動的生成、自動拡張 |
| `DIR-OOS-004` | パラメータ | NED内でのインスタンス単位の上書き |
| `DIR-OOS-005` | モデル連携 | INETモデルのインポート・対応付け |
| `DIR-OOS-006` | 結果出力 | Parquet、OMNeT++の`.vec`・`.sca`形式 |

## 3. 機能要件

### 3.1. システムの定義

#### 3.1.1. 構造・型

- <a id="dir-req-015"></a>**DIR-REQ-015**：対応範囲のNED構文を読み込み、システム構造を構築できること。
- <a id="dir-req-016"></a>**DIR-REQ-016**：`simple module`と`compound module`を定義し、サブモジュールを展開できること。
- <a id="dir-req-017"></a>**DIR-REQ-017**：パッケージ宣言と完全修飾型名を扱えること。
- <a id="dir-req-018"></a>**DIR-REQ-018**：モジュール型ごとにデフォルトパラメータを定義できること。
- <a id="dir-req-019"></a>**DIR-REQ-019**：通信端点、伝送路、共有資源を共通のシミュレーション要素として扱えること。
- <a id="dir-req-051"></a>**DIR-REQ-051**：一つのノードに、送受信、バッファリング、転送、調停などの複数のケイパビリティを組み合わせて持たせられること。

`simple module`は振る舞い実装の単位、`compound module`は子モジュールと接続による構造の単位とする。
NEDの参照版、`network`宣言、階層境界の接続、channel構文などの詳細は `DIR-TBD-002` で定める。

#### 3.1.2. ポート・接続

- <a id="dir-req-020"></a>**DIR-REQ-020**：モジュールに名前付きの入力・出力ポートを定義し、ポート間の接続を記述できること。
- <a id="dir-req-021"></a>**DIR-REQ-021**：接続元・接続先のノードとポートの存在、入出力方向、プロトコル・ポート型の互換性を検証できること。
- <a id="dir-req-022"></a>**DIR-REQ-022**：不正な接続の重複を検出できること。
- <a id="dir-req-023"></a>**DIR-REQ-023**：接続互換性はポート単位で判定できること。

### 3.2. シナリオの設定・初期化

#### 3.2.1. シナリオ・パラメータ

- <a id="dir-req-024"></a>**DIR-REQ-024**：INIでシミュレーション時間とインスタンスごとのパラメータを指定できること。
- <a id="dir-req-025"></a>**DIR-REQ-025**：NEDのモジュール型に定義されたデフォルト値に対し、INIのインスタンス別指定を優先できること。
- <a id="dir-req-026"></a>**DIR-REQ-026**：INIで上書きしないパラメータは、NEDのデフォルト値を保持すること。
- <a id="dir-req-027"></a>**DIR-REQ-027**：パラメータの型を検証し、型不整合は読み込み時にエラーとすること。
- <a id="dir-req-052"></a>**DIR-REQ-052**：時間、データ転送速度、データ量のパラメータを単位付きで扱い、異なる物理量の指定を読み込み時にエラーとすること。

NED型の値を共通のデフォルト値とし、インスタンス生成時にINIで上書きすることはDIRの値解決仕様である。
NEDの固定代入と `default(...)` の区別を含むOMNeT++全体の値解決との一致は約束しない。受理する記法は `DIR-TBD-002`、INIの具体的構文・値型・単位は `DIR-TBD-003` で定める。

#### 3.2.2. 実行モデルの生成

- <a id="dir-req-028"></a>**DIR-REQ-028**：NEDの型名とRustの振る舞い実装を対応付けられること。
- <a id="dir-req-029"></a>**DIR-REQ-029**：完全修飾型名を使って実装を識別できること。
- <a id="dir-req-030"></a>**DIR-REQ-030**：確定した構造とパラメータに基づいて、実行に必要なインスタンスを生成・初期化できること。

#### 3.2.3. 入力の検証・診断

- <a id="dir-req-053"></a>**DIR-REQ-053**：未対応の入力構文、未知の型・設定先・パラメータ、必須値の欠落、不正な接続を検出した場合、原因と対象を診断情報として示し、イベント実行を開始しないこと。

構文の受理範囲と必須パラメータは `DIR-TBD-002`・`DIR-TBD-003` で定める。エラーの表示形式は `DIR-TBD-009` で定める。

### 3.3. シミュレーションの実行

#### 3.3.1. イベント・通信

- <a id="dir-req-031"></a>**DIR-REQ-031**：イベントをシミュレーション時刻に従って実行できること。
- <a id="dir-req-032"></a>**DIR-REQ-032**：接続されたノード間でメッセージやトランザクションを転送できること。
- <a id="dir-req-033"></a>**DIR-REQ-033**：CAN、Ethernet、SoC、メモリ、IPCのモデルを共通の実行基盤で扱えること。
- <a id="dir-req-055"></a>**DIR-REQ-055**：INIで指定したシミュレーション時間に従って、イベント実行を終了できること。

終了時刻ちょうどのイベント、イベントがなくなった場合、過去時刻への予約、時刻の分解能・丸めの扱いは `DIR-TBD-004` で定める。

#### 3.3.2. 遅延

- <a id="dir-req-034"></a>**DIR-REQ-034**：処理・変換・転送・伝搬・メモリアクセスなどの遅延を、発生源ごとに扱えること。
- <a id="dir-req-035"></a>**DIR-REQ-035**：バッファでの待ち時間と共有資源の調停待ち時間を扱えること。
- <a id="dir-req-036"></a>**DIR-REQ-036**：転送量と帯域に応じた転送時間を扱えること。
- <a id="dir-req-037"></a>**DIR-REQ-037**：各遅延をイベントの実行時刻に反映できること。

#### 3.3.3. バッファ・共有資源

- <a id="dir-req-038"></a>**DIR-REQ-038**：バッファの容量と使用量を扱えること。
- <a id="dir-req-039"></a>**DIR-REQ-039**：バッファ満杯時の動作を表現できること。
- <a id="dir-req-040"></a>**DIR-REQ-040**：複数の要求による共有資源の競合を表現できること。
- <a id="dir-req-041"></a>**DIR-REQ-041**：調停方針に従って、競合する要求の処理順序を決定できること。

必須とするバッファ満杯時の動作、容量の単位、調停方式は `DIR-TBD-005` で定める。

### 3.4. 結果の記録・出力

#### 3.4.1. 性能指標

- <a id="dir-req-042"></a>**DIR-REQ-042**：キュー長、遅延、使用率、スループット、調停待ち時間を時系列で記録できること。
- <a id="dir-req-043"></a>**DIR-REQ-043**：平均遅延、最大キュー長、破棄数、平均使用率を集計値として取得できること。

#### 3.4.2. 出力形式

- <a id="dir-req-044"></a>**DIR-REQ-044**：記録した結果をCSVとJSONで出力できること。
- <a id="dir-req-054"></a>**DIR-REQ-054**：出力した各計測値について、計測対象、指標、単位、および時系列値の時刻または集計値の観測区間を識別できること。

各指標の計算方法、計測対象、記録契機、出力スキーマは `DIR-TBD-006` で定める。

### 3.5. 実行・出力の異常終了

- <a id="dir-req-056"></a>**DIR-REQ-056**：実行または結果出力の失敗を検出した場合、原因を診断情報として示し、正常終了と区別できること。

異常時の停止範囲、途中結果、具体的な通知方法は `DIR-TBD-009` で定める。
