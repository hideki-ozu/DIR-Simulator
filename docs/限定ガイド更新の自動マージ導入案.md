## 現在の運用：独自方式の廃止

標準GitHubのAllow auto-mergeは個別承認により有効化済みで、PRごとに利用者がAuto-mergeを選ぶ。全PRの自動予約はしない。main-pr-quality（ruleset 24862905）はActive、mainのみ、bypass空、PR必須・承認0人・会話解消、指定2 check/App15368/strict、force push・削除禁止を保持する。今回のコード廃止はその設定を変更しない。

## 収集・検証・処理フロー

1. trusted SHAとmain ref、main policy bytes、PRのrepository・actor・base/headを照合します。base...headのmerge baseがtrusted mainであることを要求します。
2. PRファイル一覧を全ページ取得し、changed_filesと照合します。[API上限3000件](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)以上、途中取得、重複、不一致は停止します。Git treeも全体を取得し、truncatedなら停止します。
3. treeの実差分がファイル一覧と一致し、旧新とも通常blob/mode100644であることを確認します。削除、120000 symlink、100755 executable、160000 submoduleは拒否します。renameは旧新両パスの完全一致allowlistが必要です。blob bytesをGit形式でhashしtree SHAと照合します。
4. Markdownのraw HTML・危険URI・外部画像、INIのinclude・未知設定・外部参照、JSONの未知schema・過大件数を拒否します。PNGはCRC・chunk・終端を検査し、Pillow12.3.0で完全decode/re-encodeします。隔離ビルドには再エンコード画像を使います。
5. trusted-mainの`build_guide_inputs.py --check`、MkDocs strict、リンク検査、`verify_guide.py`を実行します。固定CLIで3サンプルの数値・manifestを再現します。ZIPは対象外なので、入力変更が既存ZIPと一致しなければ停止して人のレビューへ戻します。
6. writerの適格判定には`MkDocs strict build and links`と`Guide scoped validation`の両成功が必須です。mainとheadのworkflow blob一致、正しいworkflow path/ID、pull_request event、repository、PR、head SHA、最新run/attempt、job/check/suite、GitHub Actions app ID15368を照合します。旧成功の後の失敗・queued・skipped、同名偽check、重複、欠落、取得不能は停止します。
7. 一般PRの保護はpolicyの`branch_required_checks`で別に定義し、初期値は一般品質ゲート`MkDocs strict build and links`です。`Guide scoped validation`をmain全体のrequired checkにしてはいけません。対象外コード・管理文書・別author・開始前PRのscoped検証は失敗しても、一般品質ゲートと個別レビューによる人手mergeを妨げません。writerには引き続き不適格です。既存の追加required checkや保護を削除して固定2件に合わせません。未知の追加checkはwriterを停止し、提供元をレビューしてtrusted mappingへ追加する必要があります。有効なmain rulesetにstrictと提供元、delete/force禁止、bypassなしを要求します。
8. writerはscoped validationとPages checksのどちらのworkflow完了でも再評価します。片方が未完了なら書き込まず停止し、後からもう片方が完了したイベントで再収集します。起動runをAPIで再取得し、対象PRが一つだけで、最新成功run/attemptと同一であることを確認します。Pagesのpush/dispatchイベントは対象外です。repository単位のconcurrencyとcancel-in-progress=falseで直列化し、重複イベントはclosed PRまたはmain変更で停止します。
9. PR・main・rules・全ファイル・checkをもう一度収集し、最初の結果と一致する場合だけ[head SHA指定の通常マージ](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)を実行します。追加commit、base移動、conflict、mergeable不明は停止します。最後の読取後のbase変更や追加必須checkへの対処はGitHubのstrict保護と通常merge APIにも依存します。
10. merged commitとmain refを確認後、main限定Pages dispatchにexpected_shaを渡します。dispatch run、build/deploy job、deployment SHAとrun URL、main refを追跡してから成功を報告します。

ネットワーク取得不能や未知のAPI形状も許可へ倒さず停止します。通信結果不明のマージやdispatchは再送しません。マージ済み・dispatch結果不明などの部分成功はauditに記録し、「公開成功」とは報告しません。

## 生成一覧を伴う更新の安全境界

通常の限定ガイド修正でも、push前に文書版・履歴を一改訂へ確定し、文書運用規約に従って一覧を再生成する。そのため `docs/要件トレーサビリティ一覧.md` と `.html` は、一般の編集allowlistとは別の派生物として扱う。管理文書・要件階層JSON・生成器・workflowの編集許可は増やさない。

collectorは全ページ・tree差分・通常blobのmodeとdigestを従来どおり照合し、一覧のmodifiedだけを受け付ける。追加・削除・renameは停止する。最新mainでは一覧が約2.4MBなので、派生物に限り4MBを上限とし、画像2MB・通常テキスト200KBを維持する。旧オフラインpolicyは派生物を受け付けず、HTMLを一般の安全テキストとして許可しない。

collectorはtrusted SHAと一致する清潔なcheckoutの文書を一時領域へコピーし、許可済みデータを重ねる。trusted checkoutの絶対パスから生成器を実行し、更新後の一覧2形式と要件階層HTMLの全byte一致を要求する。変更していない片側も照合し、欠落・古い一覧・任意HTML・生成失敗を許可へ倒さない。生成器が更新する階層HTMLは対象外のままで、trusted-baseの内容と一致しなければ停止する。一覧のみのPRも停止する。tokenを生成器へ渡さず、PRのscriptや依存を実行しない。

validatorでも同じ一致検査をビルド前に実行する。writerは二度のcollector収集で再生成を再確認してから既存のSHA指定merge境界へ進む。MkDocsの成功や生成ヘッダーだけを一致証拠にしない。生成器が変更されたmainへはそのmainのレビュー済み実装で追従する必要がある。今回のallowlistは従来のCAN5ガイド・画像4件・サンプル5件を維持し、新規CAN FD・Ethernetガイド全体を暗黙に許可しない。

## 標準tokenの保護証跡の判断（Issue #31）

2026-10-10に[REST ruleset仕様](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset)と[workflow permissions仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)を再確認した。前者はbypass_actorsの返却をruleset write accessがあるcallerに限定し、rulesetの作成・更新はAdministration writeを要求する。後者のGITHUB_TOKEN権限一覧にAdministrationはない。公開branch rules APIはMetadata readで有効なruleを読めるが、bypass全体が空である証明を代替しない。従って現在の標準tokenと契約だけで成立する証跡経路は確認できず、属性欠落時の停止を維持する。管理者の手動JSON、古い設定のコピー、成功したcheckや過去の非bypass記録から現在の空を推定しない。

選択肢は、(1) 無効状態を維持して通常の個別レビューで運用する、(2) 標準tokenで参照可能な権威ある証跡APIが公式に確認できた時点で再設計する、(3) 別途承認された証跡提供主体・鮮度・失効・設定変更競合の契約を設計する、の順である。(3) は資格情報・権限の変更を伴い得るため今回実装しない。GraphQLや別のtokenへの切替で隠れた属性を迂回しない。Issue #31は未解決のまま保持する。

またwriterのpermissionsでは未指定のdeploymentsがnoneになるため、現構成でdeployment読取成功を前提にできない。実tokenによる可否の試験は今回行わず、将来の明示的なdeployments:readの承認、または同等の公開完了証跡の設計が必要である。今回permissionsは変更しない。実merge・dispatch・deployment書込みは0件である。
