<a id="p-core-t01"></a>
## 2. P-CORE-T01 版・互換性・能力の受け入れ

P-CORE-D01を検証する。各候補profileの最小正常入力、全必須field欠損／未知／重複／型違い、0／上限／上限+1、版不一致、無効capabilityを個別に試す。wireはroot→adapter tagged union→packet encapsulation→port/revision所有関係を検査する。RSTP/MVRPは採用した将来revisionの設計上の受理条件を検査する。公開済みタグへの追加を意味しない。現行作業ツリーではprofileを登録し、限定revisionをprepareで受理する。設計不足を仮定したreadiness negativeは公開gate拒否を期待する。

現行全profileの入力、旧利用crateのtrait実装、V1観測、通常schema1/2の結果を基準と比較する。新MetricV2／controlled exportはschema3を明示する。未承認合成を無視して通常実行へfallbackさせない。

<a id="p-core-t02"></a>
## 3. P-CORE-T02 順序・資源・成功prefixの受け入れ

P-CORE-D02を検証する。deadline-1/deadline/deadline+1、同時刻phase0/1/2、同phase安定順、T直前／T／T直後を固定期待FES列と照合する。予約失敗はstate/FES/queue/ID/record/metricの前後hash一致で全rollback範囲を確認する。dropとcallback失敗を別caseにする。

Pause→同一時刻Resume→Exportの仮想結果を無停止runと比較する。replayはcommit ordinalだけでなくboundary_seqとsnapshot groupingを保つ。checkpointは初期化前／後の両方を保存し、restore前検査でfactory/init/finishの呼出回数も比較する。publication前失敗とrename後parent sync失敗を分ける。

<a id="p-core-t03"></a>
## 4. P-CORE-T03 観測・準備判定の受け入れ

P-CORE-D03を検証する。origin/branch/fragment/packetの参照が成功prefix内で閉じ、planned endをactual endに使わないこと、母数・空集合・null・H時刻bucketが仕様どおりであることを確認する。Viewerは通常／未送信／送信途中／完了／dropの各時刻で往復して同じ状態に戻ることを確認する。

設計gateでは`python3 scripts/check_extension_design.py`が全P要件の六工程、ID/anchor、fixture参照、再計算した期待値を検査する。checker自身のnegative testsで欠落edge、重複ID、誤算を検出する。通常のstrict trace／生成文書／MkDocs検査も実行し、結果を別記録へ残す。

## 5. 証跡と公開gate

製品試験記録にはcase ID、source commit/hash、入力hash、profile/schema、計算根拠、コマンド、実測record/summary、差分、合否、出力pathを保存する。内部故障注入には前後state/FES/journal hashも保存する。実装後はfmt/clippy/locked tests、既存回帰、生成trace strict、CLI/API例、Viewer実機確認を必須とする。

RSTP/MVRPの設計gateは2022 base本文、条項対応、選択した機械とcodec、独立設計vector、レビューを根拠に閉じた。製品gateの最終判定は製品検証記録に分離し、全guard組合せと複数bridgeの統合実行は実施範囲を個別に確認する。後続規格改訂や既存16 profileの試験を根拠へ転用しない。
