## 2. P-CORE-D01 準備と能力表

P-CORE-A01を次へ割り当てる。変更は既存componentを分割・追加して接続し、並列の独自runtimeを作らない。

| 既存入口 | 変更予定／生成する不変値 | 不対応時 |
| --- | --- | --- |
| `input/network.rs`、model-config/workload読込 | 専用exact root、局所validator→参照解決→所有表→資源上限→Frozen config | 位置付きprepare診断、実行state作成なし |
| `registry/mod.rs`、profile catalog | 明示profileとcapability。MetricV2 descriptor・codec catalog・上限設定をprepare前に凍結 | 未知profile/revision又はUnsupportedCapability |
| `runtime/registered.rs` | `Arc<PreparedSimulation>`＋owned EngineState。RunSessionから借用期間を横断しない | 未対応専用backendは通常runのみ |
| `runtime/network.rs`と各coordinator | committed stateを読み一つのNetworkDeltaを作る。新機能の状態を同じownerへ所属 | 未承認のprofile合成はprepare拒否 |

candidate profileを公開するcommitにはCLI/API docs、validator、runtime、schema、例、Viewer、製品検証を同時に接続する。プロトタイプ名を現行builtin一覧へ先行掲載しない。

<a id="composite"></a><a id="replication"></a><a id="preemption"></a>
ネットワーク3分野は[状態・入力・出力表](implementation/ネットワーク後続拡張実装設計書.md)を正とする。正規経路、queue所有者、target freeze、枝の成否と原frame母数を同じ設計から実装する。

<a id="wire"></a>
wire unionの共通wrapperは[仕様 §2.1](後続拡張契約提案仕様書.md#wire)を正とする。adapter内部のcodec／lease／機械は分野文書を正とし、独立したfield重複は置かない。RSTP/MVRPの採用版解釈と本文対応は各規範補足を参照し、抽象treeへ置き換えない。

<a id="p-core-d02"></a>
## 3. P-CORE-D02 commit・制御・永続化

P-CORE-A02を分野のstaged plannerとEngineのcommit境界へ割り当てる。処理はvalidate→derive delta→checked reserve→commit→journal publishの順とし、callback成功後のStop/Pause要求を次event popより先に取り込む。追加FES予約は既存phase/delta規則を通す。失敗後のcleanupは実行ledgerを使い、未初期化モデルをfinishしない。

<a id="control"></a>
RunSessionの状態表、要求snapshot・boundary_seq、token世代、mailbox上限、cleanup順は[実行基盤 §3](implementation/実行制御・指標・checkpoint実装設計書.md#p-control-s01)。checkpointはsubmit gateを閉じてpendingを通常順でdrainし、まだPausedの場合だけ保存する。manifest自己hashを排除し、rename publicationとparent sync durabilityを区別する。ReadyPause復元ではfactoryを呼ばない。

<a id="metric-v2"></a>
MetricV2はeffect preflightで次accumulatorとtimestamp bucketをchecked計算し、完成した値だけcommitする。Hのglobalとwindowの差を後からmin/maxの逆算で消さず、保留bucketで保持する。checkpointはこのbucketも保存する。

<a id="p-core-d03"></a>
## 4. P-CORE-D03 出力・検査・引継ぎ

P-CORE-A03をrecord/schema catalog、Exporter、Viewer、および[提案検証](後続拡張契約提案検証仕様書.md)へ割り当てる。FrozenJournalは成功prefixのviewを作り、exportはlive stateを変更しない。予定metadataとactual recordを分け、未到達値はnullを保持する。checkpointは入力byte、codec object、FES、次ID、journal offset、metric bucketを検証してprivate arenaへ復元し、全成功後だけ公開する。

設計checkerは`proposal-trace`を検査し、正式DIRのconfirmed coverageを増加させない。fixtureごとに独立再計算と構造検査のみを分けて記録する。製品試験未実施を成功に変更しない。

## 5. 実装順序と各変更の完了条件

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | 能力表・共通owned engine・validator分割 | 旧API／旧profileの回帰、prepare失敗が実行stateを作らない |
| 2 | MetricV2 | descriptor・整数batch・H bucket・schema3・窓／prefix／overflowの製品vector一致 |
| 3 | RunSession | owner poll、競合、token、同時刻、export失敗、cleanup、無停止runとの仮想結果一致 |
| 4 | Gateway＋TSN | admission／PSFP一回／RX解放／原子失敗／schema2／Viewerの製品vector一致 |
| 5 | 冗長配送、次にpreemption | 各々単独profileでsequence／回復窓、fragment／gap／T境界と参照閉包を確認 |
| 6 | IGMP、次にMLD | checksum／全6report種／lease／router／同時失効／境界wireを独立byteと状態で照合 |
| 7 | checkpoint | codec catalog、ReadyPause、往復同値、破損/版不一致、各publication故障点、復元失敗を確認 |
| 8 | RSTP、MVRP | 完了した規範補足を基準に、規範遷移／wire／timer、限定FDB flush、MVRP因果順を製品で照合 |

各順序は実装の提案で、採用の意思決定や正式要件への昇格を省略しない。標準完全実装や全組合せを初版で暗黙に約束しない。
