## 目的と読み方

利用者が、既存モデルでは評価できない通信の合成・冗長性・割込み、標準形式の制御packet、途中状態の保持、独自指標を指定できるようにする。本書は、その製品実装を開始できる入出力・状態・検証の契約を定める。承認済みの限定scopeは現行作業ツリーへ実装した。[正式採用仕様](../specs/後続拡張採用詳細機能仕様書.md)で採用範囲を、[製品検証記録](../verification/results/extension-product-2026-10-17.md)で実行結果を確認する。

順序は本書の要件→[機能仕様](後続拡張機能仕様書.md)→[詳細仕様](後続拡張契約提案仕様書.md)→[アーキテクチャ](後続拡張アーキテクチャ設計書.md)→[詳細設計](後続拡張契約提案設計書.md)→[検証仕様](後続拡張契約提案検証仕様書.md)とする。各分野の要件本文と具体的な契約は下表の分野文書に集約し、各工程の固定IDで追跡する。同じ要件を別の言葉で重複定義しない。

`P-…-Rnn/Fnn/Snn/Ann/Dnn/Tnn`は、この設計案だけの要件／機能／詳細仕様／アーキテクチャ責務／設計／検証IDである。元のP-IDを維持し、正式採用はDIR-REQ-0256〜0282へのcrosswalkで追跡する。`proposal-trace`の機械検査はこの案の工程対応だけを確認する。

## 対象と分野要件の管理先

| 分野 | 利用目的 | 要件から検証までの正本 |
| --- | --- | --- |
| P-COMPOSITE | CAN↔Ethernet変換とTAS/CBS/PSFPを同一仮想実行で評価 | [ネットワーク後続拡張実装設計書](implementation/ネットワーク後続拡張実装設計書.md) |
| P-REPLICATION | 冗長経路の遅着・重複・損失を原要求と枝に分けて評価 | 同上。非巡回sequenceによるDIR独自抽象 |
| P-PREEMPTION | fragment境界でexpressを優先する待ち時間を評価 | 同上。DIR独自抽象。MAC Mergeの完全実装とは区別 |
| P-IGMP / P-MLD | wire形式の参加通知・queryからmulticast配送状態を更新 | [IGMPv3・MLDv2-wire実装設計書](implementation/IGMPv3・MLDv2-wire実装設計書.md) |
| P-RSTP / P-MVRP | BPDU／MRP PDUとtree／VID登録を対応させる | [RSTP・MVRP-wire実装設計書](implementation/RSTP・MVRP-wire実装設計書.md) |
| P-CONTROL | 成功commit境界でPause／Export／Resume／Stopを行う | [実行制御・指標・checkpoint実装設計書](implementation/実行制御・指標・checkpoint実装設計書.md) |
| P-METRIC | 点観測と時間保持値を指定した方法で集計 | 同上 |
| P-CHECKPOINT | 対応capabilityを持つモデルの停止状態を別processへ移す | 同上。同一processのResumeTokenとは別契約 |

process越しcheckpoint（P-CHECKPOINT）は今回の設計対象に含める。初期対応は、全Model／Channelが保存・復元codecを持つ汎用registered engineに限定する。network partitionと既存専用engineのcodec追加は別対応であり、結果exportや同一processのtokenを保存対応の代用品にしない。

CAN error/retry/bus-off、確率負荷、完全FD codec、AXI複数ID、NoC virtual channel、任意機能の自動合成は今回の詳細化に含めない。既存profileの対象外一覧を、すべて今回の開発要求へ変更するものではない。

## 横断要件

<a id="p-core-r01"></a>

### P-CORE-R01 既存利用との互換性

現行のprofile、NED／INI／JSON、同期run、既存の公開traitとV1計測APIは従来どおり利用できること。新しい意味は明示profile又は明示capabilityで選び、未対応の組合せはprepare時に拒否する。新機能を選ばない実行のrecord順、整数時刻、母数、終端、出力schemaを変えない。

受入条件：既存入力の差分比較、旧APIの利用crateのコンパイル、新機能の未知field／版／不対応capabilityの拒否を別々に確認する。対応していない機能を無視して成功させない。

<a id="p-core-r02"></a>

### P-CORE-R02 決定性・所有権・有界性

一つの仮想実行は一つのFESと成功commit列を持つこと。時刻u64 ps・半開区間[0,T)、既存phase/delta/sequence規則、検査付き算術を共有する。queue、履歴、制御要求、packet、checkpointは明示上限を持ち、一callbackの状態・record・計測・予約を部分公開しない。失敗時は最後の成功prefixを出力する。

受入条件：同時刻競合、終了境界、容量0／上限／上限超過、古いtimer、callback失敗を固定期待値で検査する。再開はFES・次連番・積分器を保持し、元の入力と同じ仮想結果を出すこと。wall-clockで到着した制御要求の再現には記録したcommit境界を使う。

<a id="p-core-r03"></a>

### P-CORE-R03 観測と実装準備の根拠

origin／枝／copy／fragment／制御packetの識別子と集計母数を明示し、予定時刻を実到達へ置き換えないこと。標準wire adapterは、採用した版・role・除外機能・出典条項・具体的なpacket／状態／timerを示す。資料未取得や未確定の状態機械を実装者の裁量へ渡さない。

受入条件：各分野の全要件が六工程へ到達し、独立期待値を持つ検証vectorがあること。設計の機械検査、製品実行、標準適合は別の状態で記録する。未取得一次資料が残る場合、その分野の`design_ready`はfalseとし、何を取得・決定すれば閉じるかを列挙する。

## 設計判断を固定する方法

本案の初期実装範囲を分野文書で固定する。設定で変更できるものは名前・保存場所・型・単位・既定値・範囲・省略・0・上限・未知値を定義し、変更口のない前提は固定条件として記す。標準の定数と、DIRが選んだ制約・上限を分ける。

仕様に二つの解釈がある場合は、一つを選び、旧提案からの修正理由と影響を記録する。「実装時に検討」「標準参照だけ」「その他は適切に処理」は完了条件を満たさない。外部資料が不足する事実は、不足項目を列挙して残す。

## 実装着手と製品完了の判定

| 判定 | 必要な証拠 |
| --- | --- |
| 設計準備完了 | 要件本文、全field、状態・guard・action・timer、境界／異常、所有権、接続先、独立vector、全工程対応、未解決事項0 |
| 実装着手可能 | 上記がそろった分野を単独で選択できる。未完成adapterを含む合成profileは開始条件に入れない |
| 製品実装完了 | validator／runtime／output／CLI/API／Viewer・例・互換性試験が接続し、製品でvectorを実行した記録がある |
| 標準適合を主張可能 | 対応roleと条項を限定した適合表、独立packet・状態遷移の照合、相互接続条件・除外機能が確認済み |
