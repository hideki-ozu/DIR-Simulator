## 1. 提供状況

Linux／WSL用のローカルNEDエディタを提供する。内部テンプレートから新規作成し、NED・INI・JSONの原文と構成図を編集して、プロジェクトを別フォルダへ保存できる。NED文法と検証はシミュレータの共通parser／prepareを使う。

[仕様書](NED-editor仕様書.md)に機能範囲、[ブロック構成](NED-editor仕様書.md#block-architecture)、[詳細設計](NED-editor仕様書.md#detailed-design-map)、[検証条件](NED-editor仕様書.md#editor-verification)を記載する。結果の閲覧は別の[READMEの結果ビューア](../../../README.md#結果ビューア)を参照する。

## 2. 起動・終了

Rust 1.85.0を使い、リポジトリルートから次のように起動する。

```bash
cargo build --locked -p dir-simulator
mkdir -p /tmp/dir-editor-exports
./target/debug/dir-simulator ned-editor \
  --config examples/can/baseline.ini \
  --export-root /tmp/dir-editor-exports \
  --state-root /tmp/dir-editor-state
```

`--export-root`には保存先の親フォルダを指定する。省略時は起動したディレクトリになる。`--state-root`は復旧情報の保管先で、省略時は`${XDG_STATE_HOME:-~/.local/state}/dir-simulator/ned-editor`になる。入力フォルダ内には指定しない。

`--config`を省略すると、内部のMultibusテンプレートから`Untitled`を新規作成して開く。テンプレートはバイナリに含まれ、入力用フォルダを作成しない。

「新規プロジェクト…」では名前とテンプレートを選ぶ。既定のMultibusと単一CANはController 2個とBus 1個で開始する。Gateway設定例はBus 2個とGatewayを含み、経路設定の全項目を記載している。「空のMultibusネットワーク」は何も配置せず開始する。現在のプロジェクトを置き換える前に確認し、新規作成後は古い編集履歴を引き継がない。名前には英数字と`_`を使い、英字または`_`で開始する。最初の保存は「別フォルダに保存」を使う。

テンプレートは全標準NED型とINIの実行制限を用意する。配置済みのテンプレートには実体値・channel遅延、explicit／periodic両形式のworkloadも記載する。初期の`times=[]`と`count=0`は送信なしの設定であり、フォームでも保持できる。Gateway設定例は`processing_delay`・`hop_limit`・`rx_queue_capacity`と経路の全項目を持つ。空のテンプレートには実体別上書きや送信定義を置かず、構築途中は未完成として検証・保存を拒否する。単一CANではmodel-configを使わない。

標準出力に表示されたURLを同じマシンのブラウザで開く。URLは接続中の編集セッション専用なので、画面を開く際はfragmentを含める。待受けは`127.0.0.1`の空きポートだけで行い、ブラウザは自動起動しない。終了は起動端末でCtrl+Cを押す。

読込時にNED、INI、参照JSONを内部モデルへ複製し、入力ファイルを閉じる。以後の編集は内部モデルだけに作用する。外部で元ファイルを変更しても自動反映されない。構文不正のNEDはプロジェクト全体の読込を拒否するが、数値範囲や接続などの意味エラーは読込後に検証して修正できる。

## 3. ファイル・型・実体・構成図

左側のファイル一覧から原文を選び、型一覧から表示する定義を選ぶ。実体一覧ではnetworkから展開した配置の階層を選ぶ。型定義を複数箇所で使う場合、その型の子モジュールやdefault値の変更は全配置へ影響する。

構成図は子モジュールとgate、接続を表示する。gateのinput／outputはNEDの定義方向であり、CANのTX／RXメッセージ方向とは別の表現になる。型境界ではinputが内部への接続元、outputが内部からの接続先になる。未知型や構文不正になった依存型は未解決として表示する。

ズーム、スクロール、選択、型・実体の切替だけでは変更状態にならない。構文エラー中は最後の正常な図を古い図として表示し、構造操作を止める。原文はそのまま編集できる。

## 4. 編集

原文ペインに入力すると、入力停止後に変更を送信する。IME変換中の内容は変換確定まで送信しない。日本語・絵文字・BOM・既存の改行形式を保持する。送信中に追加した入力は、古い応答で置き換えない。

図ではパレットから子モジュールを追加し、ノードの移動・折り畳み・整列、子の削除、gate間の接続、接続先の変更・切断ができる。CANペア接続ではControllerとBusのinput／output gateを選び、TX／RXの2接続を一操作で追加する。使われているgateや不適切な方向は拒否される。

「標準部品」は開いたNEDの定義に関係なく、Controller、Bus、MultibusController、MultibusBus、Gateway、Fanoutを常に提供する。FixedDelayは接続時のchannel候補として提供する。Controller／Busは現在のプロファイルに合わせる。配置時に必要な定義を現在のNEDへ取り込み、同名の既存定義を上書きしない。保存した一式は内部テンプレートを参照せず開ける。

単一CANへGateway／Fanout／明示Multibus型を追加すると、確認後に既存Controller・Busの実装とINIをMultibusへ変更する。パラメータ値とgate名は保持し、必要なら空の経路設定JSONを追加する。配置・定義取り込み・設定変更は一回のUndoで戻せる。追加したノードの外部結線とGatewayの経路設定は利用者が行う。新しい設定ファイルを追加した場合、元への上書きは使わず別フォルダへ保存する。

「複合モジュールを作成」は空のmodule型を定義して現在の図に配置する。内部へ移動して「境界ポートを追加」を使うと、内部Controller、境界input／output、2本の内部接続を一括で追加する。「gateを追加」はmoduleの境界gate、またはBusのinput／outputの組を追加する。Busは最低2組を保持する。接続中のgateは、この型を使う他ファイルの接続も確認して削除を拒否する。先に該当接続を明示的に切断する。

上部の「ネットワーク設定」で実行時間・集計幅・イベント上限、「Gateway設定」で実際のmoduleに属するControllerポート・転送経路、「送信設定」でControllerのframeと明示時刻／周期を編集する。Gateway経路は入口1個から複数の出口を選択できる。CAN IDは10進数、データは最大8バイトの16進数、時間は`1ms`など単位付きで入力する。Gatewayのポートから通常の送信定義を生成することはできない。

プロパティではNEDのdefault literalを設定・解除する。実体階層を選び「実体値を設定」を使うと、その実体だけのINI上書きを設定できる。空欄で上書きを解除する。検証成功後の実効値は参照表示である。設定フォームは通常のINI／JSONへ反映し、Undo／Redoに対応する。未知項目や重複キーなどを含むJSONをフォームで黙って置き換えない。原文ペインも引き続き使用できる。入力参照先（ned-path・workload・model-configのパス）を変更する場合は、外部で変更して再読込する。

Undo／Redoは原文と配置の操作を戻す。最大200操作かつ差分の保持量32 MiBまでを保持する。保存後も同じセッション内では履歴を使える。再読込すると履歴を初期化する。

### UIで3Busへ分岐するGatewayを作る例

1. 新規作成で「空のMultibusネットワーク」を選ぶ。「複合モジュールを作成」で型`Router`、子`gw`を作る。
2. `gw`をダブルクリックし、境界ポートを`a`、`b`、`c`の3個追加する。境界gate名はそれぞれ`receive_a`／`send_a`などとする。内部接続は自動作成される。
3. networkへ戻り、Busを3個と外部Controllerを3個配置する。各Busの一組を外部Controllerへ「CAN TX/RX 接続」で結ぶ。もう一組は「接続」で`gw.send_a → busA.rx_a`、`busA.tx_a → gw.receive_a`のように結ぶ。残りのBusにも同様に結ぶ。input／outputは表示の方向を確認する。
4. 「Gateway設定」で`Main.gw`を選び、内部の3Controllerをポートに指定する。入口`Main.gw.a`、出口`Main.gw.b`と`Main.gw.c`、standard ID範囲256〜256の経路を追加する。
5. 「送信設定」でBus Aの外部Controllerから、ID256・データ`01020304`・明示時刻`1ms`の送信を追加する。「エラーチェック」で実行準備OKを確認し、「別フォルダに保存」する。

完成前の未接続や設定不足は図の編集を妨げない。検証・保存時に全体を確認する。保存後のシミュレーションは既存CLIの`run --config <保存先>/project.ini --output <結果フォルダ>`で行う。

## 5. 検証・保存・上書き

「エラーチェック」は未送信の入力が反映されるまで待ち、プロジェクト全体を共通prepareで検査する。診断一覧で問題を確認する。検証成功は実行準備ができたことを示し、シミュレーション実行の合格を意味しない。

通常は「別フォルダへ保存」を使う。許可された親フォルダ内の相対フォルダ名を入力し、新規または空のフォルダへ保存する。変更していない入力も含め、次の一式を出力する。

| 内容 | 出力先 |
| --- | --- |
| INI | `project.ini` |
| 全NED | `ned/0001/`以降。元のルート順と相対pathを保持 |
| workload JSON | `data/workload.json` |
| model-config JSON | `data/model-config.json` |
| 採用した配置情報 | 対応NED隣の`*.ned.layout.json` |

出力INIの参照pathだけを調整し、出力予定の一式を検証してから書き込む。意味エラーがある場合は書き込まない。元の入力を変更・削除した後でも、読込済みの内部モデルから別フォルダへ保存できる。

既存の元プロジェクトや、このセッションに登録された保存先へ保存する場合は「上書き」で対象を明示して確認する。確認後にモデルや対象ファイルが変わった場合は拒否する。外部更新、新しいNEDの出現、layoutの変更などを勝手に上書き・削除しない。再読込後にファイル集合が変わった場合は新しい別フォルダへ保存する。

保存した一式は既存CLIでも検証できる。

```bash
./target/debug/dir-simulator validate --config /tmp/dir-editor-exports/example/project.ini
```

## 6. 再読込・複数タブ・復旧

「再読込」は元プロジェクトを改めて読む。未保存内容を破棄する場合は確認する。読込候補に構文エラーがあれば既存の内部モデルを維持する。

新規プロジェクトには元ファイルがないため、再読込と元への上書きは使わない。保存後も内部モデルは新規作成時の仮想入力を保持し、登録した保存先へ明示的に上書きできる。

最初のタブが編集権を持ち、後から開いたタブは閲覧専用になる。保存先の登録も編集権が必要で、閲覧専用のままCtrl+Sで登録することはできない。編集権の取得ボタンで切り替えられる。保存や復旧などの処理中は切り替えない。通信の結果が不明な場合は操作照会を使い、同じ変更を新しい操作として重複送信しない。

複数ファイルの保存はファイル単位で公開するため、途中失敗やプロセス終了で一部だけ保存される場合がある。状態フォルダの復旧記録から、保存の完了または元の内容への復元を選ぶ。復旧が必要な間は通常の変更と保存を止める。元入力を開けない場合も、起動時に残っている復旧記録を扱える。

保存または元の内容への復元が終わると、private状態フォルダに残る当該journalのbackupを自動回収する。途中停止した回収は次回起動で再開する。未復旧記録や所有identityが不明な古い残骸を推測で削除せず、保存した出力先自体を回収処理で削除しない。

復旧状態が`finalizing`の場合は、保存先情報の確定または完了／復元後のbackup回収が終わっていない。「保存を完了」で確定・回収を再試行し、すでに完了／復元した出力を改めて変更せず、元の内容への復元には切り替えない。`invalid`の場合は復旧記録が不正か現在の登録と一致せず、診断を表示して通常編集・復旧の実行を止める。元の出力と状態フォルダの内容を保持したまま、表示された診断と記録を確認する。

復旧対象の現在bytesが記録したbefore／afterのどちらでもない場合は停止する。最初に選んだ復旧方法を途中で反転させない。全ファイルの成功が確認できた場合だけ保存完了として扱う。

## 7. 対応範囲

現行の制限付きNED文法と、シミュレータが実装するClassical CAN／Gatewayを対象にする。汎用OMNeT++ NEDのすべてを扱うエディタではない。文法は[NED詳細機能仕様書](../../specs/NED詳細機能仕様書.md)を参照する。

Linux／WSLの通常ファイルを対象にし、入力と出力でsymlinkをたどらない。保存はdescriptor基準の操作・fsync・復旧記録を使う。ブラウザ間適合、大規模入力の性能、実際の電源断を伴う耐久性は別途検証範囲を定める。実装試験と文書のトレーサビリティ検査は別の証拠として管理する。
