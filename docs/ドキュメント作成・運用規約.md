要件は「満たす条件」、詳細機能仕様は「具体的にどう振る舞うか」、設計は「どう実現するか」、検証仕様は「どう確認するか」を定める。
利用者・モデル開発者向けAPIの呼び出し契約は詳細機能仕様、内部の配送・実装方式は詳細設計で扱う。実装後のシグネチャはソース・生成API文書を参照し、同じ宣言を独立に保守しない。
全体編には概要と詳細文書へのリンクを残す。詳細を移すときは元の説明を参照へ置換し、同じ規則を複数文書で管理しない。
既存のアーキテクチャ設計書にある型・APIは概念例であり、詳細設計へ移す際も未確定事項を確定扱いにしない。
未確定事項の管理元は要件定義書の `DIR-TBD` とする。決定内容の本文は担当する仕様・設計へ置き、台帳に状態・決定先・根拠を記録する。設計判断記録は理由を残すもので、現行仕様を二重管理しない。
品質・性能・実装制約も全要件の追跡対象とする。機能の振る舞いとして確認するものは全工程を通し、機能では確認できない制約だけを第2.3節の明示した例外経路で検証へ対応付ける。初期の会話の候補・提案を、そのまま確定した要求へ昇格させない。

## 2. 文書名とバージョン管理

- `docs/` のMarkdownは、最初の見出しに正式文書名を記載し、ファイル名を **正式文書名 + `.md`** とする。日本語を使用し、プロジェクト名等を見出しだけへ付加しない。
- 同じ内容の別名ファイルを残さない。正式文書名は配置先が異なる場合も識別できる名称とし、「詳細仕様書」のように分野が分からない名前を避ける。
- ルートの `README.md` はリポジトリ入口の慣例名として例外とし、見出しはプロジェクト名とする。文書IDは `readme` とする。ソースから生成するAPI文書は生成器の配置規則に従う。
- 改訂番号、日付、`new`、`final` をファイル名へ付けない。過去の内容はGitのコミットやタグで参照する。
- 要件文書は `docs/要件定義書.md` とする。版ごとの複製を作らない。
- 文書IDはファイル名と分離した一意の英小文字・数字・ハイフンの識別子とする。各文書冒頭に `文書ID：` を記載する。既存の `requirements`、`functional-spec`、`architecture` 等は保持する。
- 図にはこの文書IDを使う。文書の表示名・配置が変わっても同じ文書ならIDを保持し、参照パスと図の `Document` コメントを更新する。
- 文書を分割・統合するときは内容の管理先を決め、新文書に一意の文書IDを付ける。図の主な掲載先が移る場合は図の文書ID・配置・名前も整合させる。
- 要件・機能のIDは文書の版・名前・節番号から独立させる。名前の変更を理由に採番し直さない。

README、記述用テンプレート、自動生成レポートを除く各プロジェクト文書は、最初の見出しの直後に文書バージョン、対象GitHubバージョン、更新履歴を記載する。テンプレートには複製先で記入する同じ項目の欄を設ける。自動生成レポートには生成元スクリプトを明記し、独立した文書版・更新履歴を設けず、手編集しない。対象GitHubバージョンには、対応するGitHub Releaseのタグを記す。Releaseがない場合は `ブランチ名 @ コミットID` を記す。

文書版は `MAJOR.MINOR.PATCH` 形式とし、上位2要素（MAJOR.MINOR）を対象GitHubバージョンに合わせる。対象がReleaseの場合はタグのMAJOR.MINORを使う。Release前にブランチとコミットを対象とする場合は、プロジェクトで予定する次のGitHubバージョンのMAJOR.MINORを使う。このプロジェクトの初回GitHubバージョンは `0.1.0` を予定しているため、現在の文書版は `0.1.PATCH` とする。

PATCHは文書ごとの改訂番号とする。新規文書の初版は `0` とし、その文書の内容を更新するたびに1ずつ増やす。GitHubのPATCHだけが変わった場合は文書版を変えない。対象GitHubバージョンのMAJOR.MINORが変わった場合は、新しいMAJOR.MINORに改訂番号 `0` を組み合わせる。各更新履歴には文書版、更新日、変更内容を記載し、冒頭の文書版を履歴の最新行と一致させる。テンプレートから文書を作るときは、対象バージョンと初版の履歴を実際の値に置き換える。

### 2.1. 機能IDと全要件からの追跡

- 機能IDは `DIR-FUNC-NNN` とし、機能仕様書で一意に定義する。章番号・要件番号・実装の型やメソッド名から生成しない。
- 名称変更や配置換えではIDを保持する。廃止IDは再利用せず、理由と後継IDを残す。責務を分割・統合する場合は新規IDと元のIDとの関係を記録する。
- 機能は入力と結果・観測可能な責務を説明できる単位とする。複数機能を組み合わせる利用フローは、構成する機能と区別して記載する。
- 機能定義にはIDに対応する固定アンカー `dir-func-NNN` を置く。参照は機能名や章番号から生成されるアンカーではなく、このアンカーを使う。
- 要件と機能は多対多で関連付ける。機能が要件を「実現する」関係と、品質・実装・互換性の「制約が適用される」関係を区別する。対象外には提供機能としてのIDを付けない。
- 対応関係は[機能仕様書の対応表](機能仕様書.md#11-要件機能受け入れ条件との対応)を管理元とし、全有効要件を一件一行で掲載する。品質・実装・互換性の制約も省略しない。別文書に手作業の逆引き表を複製せず、機能からの影響調査には機能IDの検索も使う。
- 各行に要件を満たすための機能の組み合わせと分担、機能定義の充足判断、判断根拠または不足・未確定事項、検証先を記載する。対応する責務がなければ「機能不足」と明記し、空欄や行の省略で隠さない。機能だけでは確認できない制約には、適用先と設計・実装等で必要な確認を記載する。
- 充足判断は機能名や関連IDの有無ではなく、機能を組み合わせた振る舞いが要件全体を満たすのに十分かで行う。未確定事項が期待結果にどう影響するかを示し、仕様の十分性と実装・試験の結果を分けて扱う。
- 設計・試験を具体化する際は担当する機能IDを参照し、要件・受け入れ条件へ追跡できるようにする。ID付与やリンクの存在だけで、仕様確定・実装済み・検証合格とは扱わない。
- 変更時には全有効要件の行が過不足なく一件ずつあること、IDの一意性、参照先の存在、根拠のない機能、充足判断と残課題の妥当性、設計・検証への変更影響を確認する。

### 2.2. 要件の階層・分解・充足の運用

大項目は必要な能力・目的、中項目はその能力を構成する責務、小項目は個別に充足を判断できる条件とする。三階層は目安であり、既に単独で検証できる要件へ形式的な子を作らない。
既存要件は粒度に応じて配置し直し、本文とIDを保持する。上位の複合責務を残して下位要件を追加する場合、親は子の組み合わせを要求する有効要件として扱う。義務の削除・置換が必要な場合は廃止・後継を記録する。

- 階層の管理元は要件定義書とし、各有効IDの主親ID、分解状態を一か所で管理する。根は親なしと明示する。主親は一つとし、複数分野への適用は関連・制約として記載する。
- 階層をIDへ埋め込まず、追加要件は未使用の `DIR-REQ-NNN` を採番する。配置換えでIDを変更しない。自分自身・子孫を親にせず、循環を禁止する。
- 同じ義務は既存要件を再利用する。別の親でも必要な場合は参照で共有し、同義の要件を増やさない。共有先でも適用条件・検証を確認する。
- 子要件の集合が親の正常・境界・異常時の義務を覆うか確認する。共通の「原因・対象の診断」「実行抑止」等を分解の過程で落とさない。
- 末端は現在子がないという構造上の状態であり、分解完了・仕様確定・実装可能・検証合格とは区別する。分解途中の要件は残る条件と `DIR-TBD` を示す。
- 最下位の要件は一つの検証可能な責務とし、条件・対象・期待結果を記述する。数値・境界の判断が残れば未確定と明記する。語句を分けただけで分解完了にしない。
- アルゴリズム・クラス・内部配置は原則として設計で決める。Rust採用等の明示された実装制約は要件として維持する。

記述には[要件記述テンプレート](templates/要件記述テンプレート.md)を用いる。

### 2.3. 要件から詳細仕様・設計・検証への追跡

機能に関する要件は、**要件定義書 → 機能仕様書 → 詳細機能仕様書 → アーキテクチャ設計書 → 詳細設計書 → 検証仕様書** の全工程で追跡できることを必須とする。これは責務の対応順であり、文書を一度ずつ順番に書いて終えるという意味ではない。

| 工程間 | 必須の対応内容 | 対応関係の管理元 |
| --- | --- | --- |
| 要件 → 機能 | 各有効要件を満たすための全機能・分担。親の連携・横断条件も含む | 機能仕様書第11.2節の全要件対応表 |
| 機能 → 詳細機能仕様 | 各機能を具体化する入力・規則・状態・境界・異常時の責務 | 詳細機能仕様の各項目にある `trace` 記録 |
| 詳細機能仕様 → アーキテクチャ | 各仕様上の責務を担当する構成要素・境界・連携 | アーキテクチャの各要素にある `trace` 記録 |
| アーキテクチャ → 詳細設計 | 各要素の責務を実現する処理・データ・インタフェース・不変条件 | 詳細設計の各項目にある `trace` 記録 |
| 詳細設計 → 検証 | 各確認対象に対する試験ケースまたはレビュー。上流仕様の期待結果も確認する | 検証ケースごとの `trace` 記録 |

各関係は多対多で管理する。一部の経路が通るだけでは完了とせず、対象要件に必要な全分担・全分岐が検証までつながることを確認する。共有機能を介して別の要件の検証を流用したことにしないよう、各記録に対象要件IDを列挙する。
要件と機能の既存IDを保持する。詳細仕様・アーキテクチャ・詳細設計は `文書ID#固定アンカー`、検証ケースは `DIR-TEST-NNN` と固定アンカーで識別する。節番号・見出し名・ファイル名の変更で項目の識別子を変えない。
書式・識別・経路検査の詳細は[トレーサビリティ管理規約](トレーサビリティ管理規約.md)を正とする。

全経路の一覧は[Markdown版](要件トレーサビリティ一覧.md)と[HTML版](要件トレーサビリティ一覧.html)を正本データから生成する。横方向の表は要件・機能・詳細機能仕様・アーキテクチャ・詳細設計・検証を実際の隣接工程の関係に沿って示し、全ての分岐と未完了項目を残す。受け入れ条件は別表で管理し、HTML版も要件や設計項目へのリンクには対応するMarkdown文書を使う。GitHubでは埋込みCSSが反映されない場合があるため、背景色を含めて読むときはHTML版をローカルのブラウザーで開く。接続状態は色と併記する文字ラベルでも確認する。

下流項目の `upstream` に直前の工程の項目IDを登録し、対応先の本文へのリンクと分担説明を併記する。この記録を工程間対応の管理元とし、上流からの参照と変更影響の逆引きは同じ記録から確認する。手作業の全体逆引き表を複製しない。機能仕様書第1.2節と設計書冒頭の作成先一覧は作業計画であり、経路成立の証拠ではない。要件の共有だけで工程間の辺を推測せず、一覧では異なる要件間で同じ下流IDを共有しても各要件の行に個別に表示する。
未作成の上流に架空のIDやリンクを置かず、空の `upstream` と `pending` に不足工程・残課題を記す。未作成・未確定・対応漏れを区別し、未完了の記録を経路完了と数えない。

実装言語・独立実装・出自・互換性非目標など、機能の振る舞いでは確認できない制約は、要件定義書の例外記録に理由と代替経路を明示し、検証仕様のレビューケースへ直接対応付ける。未作成や実装の都合を理由に工程を省略しない。例外も全要件の検査対象に含め、検証先がなければ未完了とする。
ブラックボックス試験の期待値は要件・詳細機能仕様から独立に求める。検証対象の設計責務への対応を記録しても、期待結果を実装から生成しない。内部の所有権・資源解放等は別の設計検証・レビューに割り当てる。

親の充足には、子の集合による親本文の網羅、全必要条件の充足、子同士の連携と横断制約の確認が必要である。子要件のACは第3.6節などで明示的に割り当て、親から暗黙に継承しない。
「分解の十分性」「機能定義の十分性」「工程間の追跡完備」「仕様・設計の確定」「実装・検証の合格」は別に判断する。機械検査は参照構造を確認するもので、内容の十分性と試験合格を証明しない。

実行結果には対象コミット・環境・入力・期待値の根拠・実測値・合否・証跡の所在を記録する。未実行・保留・不合格・合格を区別し、未確定仕様に依存するケースは合格扱いにしない。

### 2.4. 詳細文書の記述・レビュー・更新手順

次のテンプレートを複製し、正式文書名・ファイル名・一意の文書IDを付けて作成する。テンプレートの例や空欄は確定仕様ではない。

| 種別 | 必須の内容 | テンプレート |
| --- | --- | --- |
| 詳細機能仕様 | 項目の固定ID、対象要件・直前の機能、分担、入出力・規則・境界・異常・具体例 | [詳細機能仕様書テンプレート](templates/詳細機能仕様書テンプレート.md) |
| アーキテクチャ | 要素の固定ID、対象要件・直前の詳細機能仕様、責務・境界・連携・設計への割当 | [アーキテクチャ設計書テンプレート](templates/アーキテクチャ設計書テンプレート.md) |
| 詳細設計 | 項目の固定ID、担当アーキテクチャ要素、根拠仕様、データ・不変条件・API・検証対象 | [詳細設計書テンプレート](templates/詳細設計書テンプレート.md) |
| 検証仕様 | ケースID、担当する詳細設計項目、上流要件・機能・AC・詳細仕様、入力・期待結果・証跡 | [検証仕様書テンプレート](templates/検証仕様書テンプレート.md) |
| 設計判断 | 論点、制約、選択肢、採用理由、影響、決定先、後継 | [設計判断記録テンプレート](templates/設計判断記録テンプレート.md) |

1. 対象範囲と代表シナリオを選び、既存要件の階層と分解漏れを確認する。新しい要求を導出する場合は理由を記録する。
2. 関連 `DIR-TBD` と判断が必要な事項を洗い出し、詳細機能仕様に候補・決定済みを区別して記載する。プロジェクトオーナーの決定責任は要件定義書に従う。
3. 正常・境界・異常の具体的入力と期待結果を作り、要件と詳細仕様の十分性をレビューする。単に全項目を埋めたことを完了条件にしない。
4. 詳細機能仕様の責務をアーキテクチャ要素へ割り当て、その要素を詳細設計で具体化し、各確認対象を検証ケースへ割り当てる。仕様と設計の食い違いは上流へ戻して整合させる。
5. 変更項目から上流根拠・下流影響を逆引きし、同じ変更で親子関係、全要件対応表、各工程のtrace記録、AC・TBD、図・リンクを更新する。分割・廃止時は旧IDの後継を本文に残し、残存参照を解消する。
6. 実装・検証後は実行結果を残す。仕様変更による再検証範囲を明記し、古いコミットでの合格を新しい仕様の証拠として使わない。

文書状態は「草案」「レビュー中」「確定」「廃止」を本文に記載する。確定時はレビュー根拠・対象範囲を残す。部分確定の場合は節または対象要件で範囲を明示し、未解消の事項を残す。履歴資料を作成・保管する場合は、取得日・収録範囲で来歴を管理し、現行仕様の確定状態とは区別する。
確定した仕様の変更案は、変更する範囲を再レビューする。既存の確定内容まで理由なく未確定に戻さず、状態の変更と理由をGitの差分で追跡できるようにする。

実装へ進む対象範囲では、全工程の経路検査（例外を含む）を通し、各工程の上流割当と検証対象の網羅をレビューしたうえで、要件の分解漏れがなく、振る舞いを変える未確定事項が解消し、入出力・境界・異常時を実装者が独断で補わずに作れ、検証者が期待結果を定められることを確認する。ほかの分野の未確定事項が残るだけで独立した範囲の実装まで止めない。候補比較や試作は、その目的と未確定の前提を明示して実施できる。

### 2.5. 文書変更時の検証項目

- `docs/` 内の正式文書名とファイル名、文書IDの存在・一意性、相対リンク・明示アンカーを確認する。引用した過去の会話やコード例のパスは現行文書へのリンクと区別する。
- 要件定義・親子表・全要件対応表のID集合が一致し、重複・存在しない親・循環がないことを確認する。
- 既存IDの意味を保ち、子への分解で元の義務が欠けていないことをレビューする。末端の具体化待ちと機能不足を隠さない。
- 機能・AC・TBD・検証ケースの参照先を確認し、各末端の検証先と親の統合検証を点検する。
- 各対象要件の全分担が6工程（登録した制約例外は代替経路）を通るか、途中で終わる分岐・根拠のない項目・未登録の仕様／設計／ケースがないか確認する。既存リンクが有効なだけでは完了にしない。
- `python3 scripts/check_traceability.py` で登録の整合性と残課題を確認する。実装へ進む範囲は `--strict --requirement DIR-REQ-NNN`、全体の追跡完備は `--strict` を使用する。欠落やpendingを残したまま厳格検査を合格扱いにしない。
- 名前変更時はREADMEと現行文書のパス、図の掲載先コメントを更新する。文書IDを保持する改名で図のファイル名を変更しない。
- 図は第8章に従って生成・確認する。文書変更だけの場合、コードの振る舞いを確認しない試験を追加せず、文書の構造・参照・内容の整合性を検証する。

## 3. 図の記述・公開形式

図の編集元はPlantUMLの `.puml`、Markdownでの表示用画像は `.svg` とする。
両方をGitで管理し、図の変更と生成画像の更新を同じコミットに含める。
生成したSVGは直接編集しない。

SVGを扱えない提出先にはPNGを生成する。PNGは通常の管理対象には加えず、必要時の配布物として扱う。
PDFはMarkdown本文と生成画像から作る文書全体の配布・印刷用成果物とし、別の編集元にはしない。

現行の仕様書・設計書に掲載する構成図・処理フローなどはPlantUMLに統一する。
コード例、ディレクトリツリー、図ではない単純な列挙はテキストのまま記載できる。
図を更新するときは、未確定の仕様・設計を補完・確定しない。

## 4. ディレクトリ構成と詳細化する分野

以下は採用する配置構成である。分野別の仕様・設計・検証ケースは必要な分野から作成する。列挙したパスは作成先であり、作成済みを意味しない。

```text
docs/
├── 要件定義書.md
├── 機能仕様書.md
├── アーキテクチャ設計書.md
├── ドキュメント作成・運用規約.md
├── トレーサビリティ管理規約.md
├── specs/
│   ├── NED詳細機能仕様書.md
│   ├── 設定詳細機能仕様書.md
│   ├── 実行詳細機能仕様書.md
│   ├── 資源詳細機能仕様書.md
│   ├── 結果詳細機能仕様書.md
│   ├── 診断詳細機能仕様書.md
│   ├── インタフェース詳細機能仕様書.md
│   └── models/
│       ├── 通信ネットワークモデル詳細機能仕様書.md
│       ├── SoCモデル詳細機能仕様書.md
│       ├── メモリモデル詳細機能仕様書.md
│       └── IPCモデル詳細機能仕様書.md
├── design/
│   ├── モデル読み込み詳細設計書.md
│   ├── 実行詳細設計書.md
│   ├── モデル構成要素詳細設計書.md
│   └── 結果処理詳細設計書.md
├── verification/
│   ├── 検証計画書.md
│   └── cases/                       # 分野名を含む検証仕様書
├── decisions/                       # 判断の対象を含む設計判断記録
├── templates/                       # 本規約から参照する記述テンプレート
└── diagrams/
    └── architecture/
        ├── architecture--simulation-pipeline--activity.puml
        └── architecture--simulation-pipeline--activity.svg
```

| 分野 | 詳細機能仕様で決める内容 | 主な未確定事項 | 作成時の文書ID |
| --- | --- | --- | --- |
| NED | 受理構文、型・階層・ポート・接続の意味、拒否条件 | `DIR-TBD-002` | `spec-ned` |
| 設定 | INI記法、設定先、値の優先順位、型・単位・必須値 | `DIR-TBD-003` | `spec-configuration` |
| 実行 | 時刻、同時刻順序、初期化、通知、終了、再現性 | `DIR-TBD-004`・`DIR-TBD-009` | `spec-runtime` |
| 資源 | 遅延の計算境界、容量、占有、競合、満杯時動作、調停 | `DIR-TBD-001`・`DIR-TBD-005` | `spec-resources` |
| 結果 | 指標の定義・計算式、記録契機、集計、CSV・JSONの必須項目 | `DIR-TBD-006` | `spec-results` |
| 診断 | 原因・対象、エラー分類、停止範囲、途中結果、通知 | `DIR-TBD-009` | `spec-diagnostics` |
| インタフェース | 利用者・モデル開発者の操作・呼び出し契約、環境 | `DIR-TBD-007`・`DIR-TBD-009` | `spec-interfaces` |
| 個別モデル | 再現・省略する現象、パラメータ、計算、代表シナリオ、適用限界 | `DIR-TBD-001`・`DIR-TBD-008` | `spec-network-models` / `spec-soc-models` / `spec-memory-models` / `spec-ipc-models` |

詳細設計の文書IDは配置例の順に `design-model-loading`、`design-runtime`、`design-model-components`、`design-results` とする。
一緒に決める規則を同じ文書へまとめ、機能IDやクラスごとに一ファイルへ固定しない。共通規則は一か所を正とし、個別モデルから参照する。文書間で異なる前提を置く場合はその適用範囲を明記する。

図は `docs/diagrams/<文書ID>/` に置き、ソースと生成SVGを隣に配置する。例えば実行詳細機能仕様書の図は `diagrams/spec-runtime/` とする。
複数文書で使う図は主な掲載先の配下に一つだけ置く。共通スタイルは `diagrams/_includes/` の `.iuml` とし、単独の画像生成対象に含めない。
配布用PNG・PDFや一時的な検証成果物は `target/docs/` に置く。常時参照するSVGは文書別ディレクトリでGit管理する。

## 5. 図のファイル名

```text
<文書ID>--<対象・内容>--<図の種類>.puml
<文書ID>--<対象・内容>--<図の種類>.svg
```

- 項目間は `--`、項目内の単語間は `-` で区切る。各項目は英小文字・数字で始まる `kebab-case` とする。
- `.puml`、`.svg`、配布用の `.png` は拡張子以外を完全に一致させる。
- 対象には `parameter-resolution` のように図が説明する内容を書く。`overview`、`flow`、`diagram1` だけの名前は避ける。
- 章番号や図の通し番号は含めない。章の並べ替えだけでファイルを改名しない。
- 同じ対象の図が複数ある場合は、`runtime-initialization`、`runtime-event-loop` のように内容を分ける。
- ディレクトリ名とファイル名の文書IDの重複は許容する。画像を単独で取り出しても出所を識別できるようにするためである。

| 内容 | ファイル名の例（拡張子を除く） |
| --- | --- |
| 入力から結果出力までの処理 | `architecture--simulation-pipeline--activity` |
| パラメータの解決 | `architecture--parameter-resolution--activity` |
| NEDの解析処理 | `architecture--ned-parsing--activity` |
| 実行ライフサイクル | `architecture--runtime-lifecycle--activity` |
| イベント配送の呼び出し関係 | `architecture--event-dispatch--sequence` |
| システム境界と利用者 | `architecture--system-context--c4-context` |

## 6. 図の種類とソース内の情報

| ファイル名の末尾 | 用途 |
| --- | --- |
| `activity` | 処理順序、分岐、繰り返し |
| `sequence` | 呼び出し、メッセージ交換、応答の順序 |
| `component` | 構成要素の責務と依存関係 |
| `class` | 型やインタフェースの関係 |
| `state` | 状態と遷移 |
| `deployment` | 実行環境への配置 |
| `c4-context` | システム境界、利用者、外部システム |
| `c4-container` | システム内部のアプリケーションやデータストア |
| `c4-component` | コンテナ内部の構成要素 |
| `c4-dynamic` | C4の構成要素間のやり取り |
| `c4-deployment` | C4の構成要素の実行環境への配置 |

表現する内容に応じて種類を選ぶ。処理パイプラインを無理にC4へ変換せず、Rustのcrateを機械的にC4のコンテナと対応付けない。
必要な種類が表にない場合は、本規約へ用途と末尾を追加してから使用する。

一つの `.puml` に一つの図を定義し、`@startuml` の名前はファイル名から拡張子を除いたものと一致させる。
先頭には掲載文書、節の見出し、図の目的をコメントで記載する。
`Document` は `.puml` から掲載文書への相対パス、`Section` は節番号を除いた見出しとする。

```plantuml
@startuml architecture--parameter-resolution--activity
' Document: ../../アーキテクチャ設計書.md
' Section: Parameter Model
' Purpose: NEDの既定値とINIの上書きからパラメータを解決する流れ

skinparam defaultFontName Noto Sans CJK JP
title パラメータ解決の流れ

' この位置に図の定義を記述する
@enduml
```

図のタイトルやラベルには日本語を使用できる。図で補足した説明は本文の要件・設計と整合させる。
大きな図は目的ごとに分け、通常の閲覧幅とPDF出力時の文字サイズを確認する。

## 7. Markdownからの参照

画像は相対パスで参照し、内容を表す代替テキストとソースへのリンクを付ける。
次は `docs/アーキテクチャ設計書.md` に記載する例である。

```markdown
![パラメータ解決の流れ](diagrams/architecture/architecture--parameter-resolution--activity.svg)

[図のソース](diagrams/architecture/architecture--parameter-resolution--activity.puml)
```

Markdownには図のPlantUML定義を重複して埋め込まず、`.puml` を編集元とする。
本書のように記述方法を説明するためのコード例はこの限りではない。
閲覧者がPlantUMLやVS Code拡張を導入しなくても、生成済み画像で文書を読めるようにする。

## 8. 生成・更新・検証

1. 掲載文書の説明と `.puml` を更新する。
2. 同じ生成環境でSVGを再生成する。共通定義を変更した場合は、その定義を使う図をすべて再生成する。
3. 日本語、矢印、文字の重なり、表示サイズ、本文との整合を確認する。
4. 命名、リンク、ソースと画像の対応を点検し、削除・改名した図の古い生成物を残さない。
5. Markdown・`.puml`・`.svg` の変更を一緒にレビューしてコミットする。

PlantUMLはローカルで実行する。C4はJARに同梱された標準ライブラリを読み込む。
例えば `!include <C4/C4_Context>` を使用し、生成のたびに外部URLから定義を取得する方法は使わない。
追加の外部資産が必要な場合は、取得元・版・利用条件を確認してローカルに固定する。

PlantUML、Graphviz、C4ライブラリ、日本語フォントの版を揃え、生成環境を更新した際は画像の差分も確認する。
この規約の整備時点で確認した環境はPlantUML 1.2026.8、同梱C4-PlantUML 2.13.0、UbuntuのGraphvizパッケージ `2.42.2-9ubuntu0.1`（`dot -V` は `2.43.0`）、日本語フォント `Noto Sans CJK JP` である。
フォントの版を含む再現可能な環境定義の固定化は、別途整備する。

図を配置した後は、リポジトリのルートで次のコマンドを実行すると全ての `.puml` を再帰的に生成できる。`@startuml` の名前はファイル名（拡張子なし）と一致させる。生成SVGは入力ファイルと同じディレクトリに同名で出力される。

```bash
python3 scripts/render_diagrams.py
```

保存済みSVGと再生成結果の一致は次で確認する。Gitのコミット内容との比較ではない。`--check` は各図を一時的な絶対パスの出力先へ生成して比較するため、既存SVGを変更しない。生成失敗、SVGの欠落、または内容の差異があれば非ゼロで終了する。

```bash
python3 scripts/render_diagrams.py --check
```

別のディレクトリから実行するときはスクリプトの絶対パスを指定する。入力・出力先はカレントディレクトリによらずリポジトリを基準に解決する。

CIへの組み込み、未追跡・不要な生成物とリンク切れの自動検出、PDF生成のツール・コマンドは未整備である。

## 9. PDFと配布物

PDFはレビューや配布で必要になった時点のMarkdownと画像から生成し、表紙または奥付に生成日と対象コミットを記載する。
配布版はコミット済みの入力から生成し、対応するソースを特定できるようにする。
日本語フォント、図の欠け、改ページ、リンクを確認する。
PDF生成のツール・コマンドは別途整備する。PNGやPDFを手作業で修正して、編集元と異なる版を維持しない。

## 10. NASAの指針との関係

要件定義ではNASAの要件記述・検証の指針を参考にする。
文書・図の識別、命名、保存、生成ツールと入力・出力の管理については、NASAのSoftware Configuration Management Plan（SCMP）の考え方を参考にする。
本書はプロジェクト独自の作成・運用規約であり、NASA所定の文書名や、NASAの文書体系全体への準拠を表明するものではない。

コードを含む変更管理やリリース管理まで対象を広げる場合は、構成管理計画書との役割分担を別途定める。

- [NASA Documentation Guidance](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695654/7.18+-+Documentation+Guidance)：文書種別と推奨内容。
- [NASA Software Configuration Management Plan](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695666/5.06+-+SCMP+-+Software+Configuration+Management+Plan)：特に第3.4節の命名・識別・生成物管理。
- [NASA How to Write a Good Requirement](https://www.nasa.gov/reference/appendix-c-how-to-write-a-good-requirement/)：要件記述の指針。
- [NASA Requirements Verification Matrix](https://www.nasa.gov/reference/appendix-d-requirements-verification-matrix/)：要件と検証の対応。
- [PlantUML Command Line](https://plantuml.com/command-line)：ローカル生成の方法。
- [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML)：C4の記述と標準ライブラリの利用。
