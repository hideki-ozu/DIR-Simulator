### 1.1. 機能の識別と粒度

機能IDは `DIR-FUNC-001` から付番する。名称変更・節の移動・追記では既存IDを変更しない。廃止したIDは再利用せず、廃止理由と後継ID（ある場合）を定義元に残す。
機能は入出力や観測可能な責務を説明・検証できる単位とし、章、要件、クラス、メソッドと一対一に固定しない。
機能を分割・統合して責務が変わる場合は新しいIDを付け、元のIDを廃止して後継との関係を記録する。

各機能の表にある明示アンカー `dir-func-NNN` を参照先とする。機能名や章番号の変更でリンクを変えない。
IDの付与は実装完了や仕様確定を意味しない。すべて本書の草案状態を引き継ぎ、機能ごとの未確定事項は第11章の対応表から確認する。

| 機能ID | 機能名 | 責務 |

| <a id="dir-func-003"></a>**DIR-FUNC-003** | モジュール階層の展開 | simple / compoundとサブモジュールから実行対象の階層を構成する。 |
| <a id="dir-func-004"></a>**DIR-FUNC-004** | パッケージ・型名の解決 | パッケージ宣言と完全修飾型名を扱い、参照する型を識別する。 |
| <a id="dir-func-005"></a>**DIR-FUNC-005** | ポート定義と接続検証 | 名前付き入出力ポートを扱い、存在・方向・型互換性・不正な重複を判定する。 |
| <a id="dir-func-006"></a>**DIR-FUNC-006** | 共通モデルとケイパビリティの構成 | 通信端点・伝送路・共有資源を共通のシミュレーション要素として扱い、一つのノードに必要な能力を組み合わせる。 |

### 3.1. 現行要件に基づく振る舞い

- `simple module` は振る舞いの実装単位、`compound module` は子モジュールと接続からなる構造の単位とする。
- パッケージ宣言と完全修飾型名を扱い、compoundのサブモジュールを展開してインスタンスと接続を構成する。
- デフォルトパラメータはモジュール型に定義する。インスタンス別の上書きは第4章に従う。
- モジュールに名前付き入力・出力ポートを定義し、接続元・先の存在、方向、プロトコル・ポート型の互換性、不正な重複を検証する。
- 接続可否はポート単位で判定する。一つのノードに複数のケイパビリティを組み合わせられることと、各ポートの接続互換性を区別する。
- 未対応構文、未知の型、不正接続を検出した場合は原因と対象を示し、イベント実行を開始しない。

モジュール継承・`import`、動的・条件付き構造、モジュールベクトル、`inout`・ゲートベクトル、NED内でのインスタンス単位の上書きなどは、要件定義の `DIR-OOS-001`〜`DIR-OOS-004` に従い対象外とする。
列挙していない構文が自動的に対応範囲に入るわけではない。

### 3.2. 未確定の仕様

`DIR-TBD-002` でNEDの参照版と受理構文一覧を定める。特に以下を明文化する。

- `network`、compound境界のゲート接続、channel宣言・指定、プロパティ、式の扱い。
- 固定代入と `default(...)` の受理記法、複数ファイルの探索、名前解決。
- NEDのゲートとポート型情報の対応、重複接続と未接続の判定条件。

パーサとモデル解決器の実装前に、受理する最小入力と拒否する入力を対にして用意する。
具体的なNED例は構文確定後に追加し、OMNeT++の例を無条件に有効なDIR入力として扱わない。

## 4. INI・パラメータ解決

| 機能ID | 機能名 | 責務 |
| --- | --- | --- |
| <a id="dir-func-007"></a>**DIR-FUNC-007** | INIシナリオの読み込み | シミュレーション時間とインスタンス別の設定を読み取る。 |
| <a id="dir-func-008"></a>**DIR-FUNC-008** | インスタンス別パラメータの解決 | 型のデフォルト値を基にINIの指定を適用し、未指定値と他インスタンスの値を保持する。 |
| <a id="dir-func-009"></a>**DIR-FUNC-009** | パラメータの型・物理量の検証と換算 | 値の型と物理量を検証し、対応単位を換算する。 |

### 4.1. 解決規則

同じ型の各インスタンスは、その型に定義されたデフォルト値を基にパラメータを解決する。
INIで指定されたインスタンスのパラメータだけを上書きし、未指定の値と他インスタンスの値はデフォルト値を保持する。
INIの指定先、パラメータ名、値の型、物理量を検証し、不正な入力ではイベント実行を開始しない。
対応する単位表記の換算と、シミュレーション時刻への丸めは区別して定める。

以下は解決結果を説明する抽象例であり、NED・INIの具体的な構文や採用単位を定義するものではない。

| 入力条件 | 期待する振る舞い |
| --- | --- |
| 同じ型のA・Bがあり、パラメータpのデフォルト値はd。A.pのみ有効な値xを指定 | A.pはx、B.pはdになる |
| 有効なデフォルト値があり、INIにそのパラメータの指定がない | デフォルト値を保持する |
| パラメータの宣言型に合わない値を指定 | 読み込み時に型不整合を検出し、イベント実行を開始しない |
| 時間パラメータにデータ転送速度の物理量を指定 | 単位・物理量の不整合を検出し、イベント実行を開始しない |
| 未知のインスタンス、未知のパラメータ、必須値の欠落 | 原因と対象を診断し、イベント実行を開始しない |
| 対応単位による同一物理量の等価表記を指定 | 換算後の値が一致することを検証する。採用単位は未確定 |

この優先順位はDIRの値解決仕様であり、NEDの固定代入・`default(...)` を含むOMNeT++の値解決全体との一致を保証しない。
INIは必要最小限の独自仕様とし、`omnetpp.ini` との完全互換を前提としない。

### 4.2. 未確定の仕様

`DIR-TBD-003` で節・キー、階層インスタンスの指定、重複キー、必須値、対応値型、許容範囲、単位と換算を定める。
ワイルドカード、設定継承、式の採否も明示する。重複キーについて「先勝ち」「後勝ち」「エラー」のいずれかを実装者が暗黙に選ばない。
時刻の分解能・丸めは `DIR-TBD-004`、不正値の具体的な診断形式は `DIR-TBD-009` と合わせて決める。

| 機能ID | 機能名 | 責務 |

| <a id="dir-func-010"></a>**DIR-FUNC-010** | 型と振る舞い実装の対応付け | 完全修飾型名を使って対応するRustの振る舞い実装を識別する。 |
| <a id="dir-func-011"></a>**DIR-FUNC-011** | 実行インスタンスの生成・初期化 | 確定した構造・パラメータ・実装から実行インスタンスを生成し、初期化する。 |

simple moduleに対応する振る舞い実装を解決する。compoundは構造として展開するという既存設計方針に従い、compound自体のRust factoryは要求しない。
未知・未登録の型を別の実装に暗黙に置き換えず、イベント実行前に診断する。

初期化の二重実行を避ける方針は既存の[アーキテクチャ設計書](アーキテクチャ設計書.md#23-runtime-flow)に示されている。
初期化の順序、初期イベントの登録契機、初期化中の失敗と終了処理は `DIR-TBD-009` で定める。
`initialize()` の直接呼び出しと初期化イベントのどちらを採るか、本書の追加で確定しない。
Timerの通知がモデルに届く契約とRust APIの通知経路は、時間仕様と設計を対応付けて解消する（`DIR-TBD-004`・`DIR-TBD-009`）。

確認時は、完全修飾型名と選択された振る舞い実装、インスタンスごとの確定パラメータを対応付ける。
登録API、factoryの型、内部ID、構造体のレイアウトはアーキテクチャ設計で扱う。

## 6. イベント・時間・終了・再現性

| 機能ID | 機能名 | 責務 |
| --- | --- | --- |
| <a id="dir-func-012"></a>**DIR-FUNC-012** | イベントの時刻順処理 | シミュレーション時刻に従ってイベントを処理する。 |
| <a id="dir-func-013"></a>**DIR-FUNC-013** | メッセージ・トランザクションの転送 | 共通実行基盤で接続先への通信・要求応答・IPCの転送を扱う。 |
| <a id="dir-func-014"></a>**DIR-FUNC-014** | 実行終了の制御 | 指定したシミュレーション時間を実行終了に反映する。 |

### 6.1. 現行要件に基づく振る舞い

- イベントはシミュレーション時刻に従って処理し、接続されたノード間でメッセージ・トランザクションを転送する。
- 通信、メモリ要求・応答、IPCの各モデルを共通の実行基盤で扱う。各モデルの具体的な振る舞いは第10章に従う。
- INIで指定したシミュレーション時間を終了に反映する。
- 同一実装版・実行環境・モデル・シナリオ・初期条件では、同時刻イベントを含め、イベント処理順序と計測結果が一致するようにする。

同時刻イベントの決定性は機能上の契約である。設計案の `(time, sequence_number)` によるキュー管理は、その実現方式として区別する。
初期イベントや実行中に追加するイベントの登録順も含め、利用者が期待順序を判断できる規則を実行エンジンの実装前に具体化する。

### 6.2. 境界条件と未確定の仕様

終了時刻をTと呼ぶ。Tの算出基準も含めて `DIR-TBD-004` で定義し、以下の期待結果を確定する。

| 条件 | 現在の扱い |
| --- | --- |
| 通常の実行範囲内に異なる時刻のイベントがある | 時刻に従った処理順序を確認する |
| 同じ時刻に複数のイベントがある | 決定的であることは必須。具体的な優先順序・追加順の規則は要定義 |
| 時刻Tちょうどのイベントがある | 実行するかどうかは未確定 |
| Tを越えるイベントだけが残る | 打ち切り時の最終時刻、未処理イベント・要求の扱いを定める |
| Tより前にイベントが尽きる | 終了時刻・終了理由と計測区間の扱いは未確定 |
| 現在より過去の時刻へ予約する | 拒否・診断などの扱いは未確定 |
| ゼロ遅延のイベントが連続して生成される | 実行順序と進行しない場合の扱いは未確定 |
| 入力時刻が表現範囲外、または分解能に合わない | 範囲・丸め・エラー条件は未確定 |

時刻の基準、分解能、範囲、丸めを固定してから、境界の前後を含む入力と期待結果を用意する。
イベント枯渇や途中終了と指標の観測区間は `DIR-TBD-006`、異常として扱う条件は `DIR-TBD-009` と整合させる。
異なる環境間の一致、精度・許容差は `DIR-TBD-008` で定める。乱数機能やseed指定は採用済みとしない。

## 7. 遅延・バッファ・共有資源

| 機能ID | 機能名 | 責務 |
| --- | --- | --- |
| <a id="dir-func-015"></a>**DIR-FUNC-015** | 遅延・転送時間の反映 | 発生源ごとの遅延と転送量・帯域に基づく時間をイベント時刻へ反映する。 |
| <a id="dir-func-016"></a>**DIR-FUNC-016** | バッファの管理 | 容量・使用量・満杯時の動作とバッファ待ちを扱う。 |
| <a id="dir-func-017"></a>**DIR-FUNC-017** | 共有資源の競合・調停 | 複数要求の競合と調停待ちを扱い、調停方針に従って処理順序を決める。 |

### 7.1. 遅延と転送時間

処理、変換、転送、伝搬、メモリアクセスなどの遅延を発生源ごとに扱い、イベントの実行時刻に反映する。
転送時間は転送量と帯域を反映する。バッファ待ちと共有資源の調停待ちも区別して扱う。
非競合時の到着時刻を独立した計算結果と比較し、競合を追加した場合には待ち時間を別に検証する。同じ遅延を二重に加算しないことを確認する。

個別モデルの転送単位、固定オーバーヘッド、遅延の重なりなどのモデル化粒度は `DIR-TBD-001`、時刻への丸めは `DIR-TBD-004`、許容差は `DIR-TBD-008` で定める。
全モデルに共通する単一の転送式や実測精度を、この段階では保証しない。

### 7.2. バッファと調停

バッファの容量・使用量・満杯時の動作、共有資源への複数要求の競合、調停方針に従った処理順序を表現する。
確認には空、容量ちょうど、容量超過と複数の同時要求を含める。

`DIR-TBD-005` で容量単位、ゼロ容量、必須の満杯時動作、調停方式、同優先度要求の扱いを定める。
設計書のDropNewest、Backpressure、RoundRobinなどは候補であり、すべての方式を提供する約束ではない。
プロトコル固有の調停と共通資源の調停の再現範囲は `DIR-TBD-001` と合わせて定める。

### 11.3. 現時点の判断と対象範囲

全90要件（既存51件と新規子要件39件）の行を掲載しているが、これは全要件を満たせると確認したことを意味しない。
現時点の機能定義の判断は、定義上充足2件、具体化待ち84件、機能外確認待ち4件、機能不足0件である。
定義上充足の2件は有効な入力に対する値の優先・保持規則についての判断であり、具体的なNED・INI入力による実装検証は残る。
機能不足0件は、現行の抽象的な責務との照合で欠落を特定していないという意味である。仕様を具体化した結果、必要な責務が見つかれば判断を更新し、機能を追加・見直す。
特に個別モデルは名前と担当機能だけでは十分性を確認できず、再現範囲と期待結果の確定が必要である。

欠番の `DIR-REQ-009`〜`DIR-REQ-014` は有効要件に含めない。移行先の `DIR-OOS-001`〜`DIR-OOS-006` は対象範囲の境界であり、提供機能のIDを付けず、第3・4・8・10章と `DIR-AC-011` で照合する。
共通の性能・精度・異環境間の保証範囲は `DIR-TBD-008` に従う。対応表の作成によって保証範囲や対象外を変更しない。

### 11.4. 設計・試験への追跡と変更時の確認

詳細機能仕様→アーキテクチャ→詳細設計→検証仕様の隣接工程を省略せず、各下流項目のtrace記録に直前の担当元を登録する。設計要素は根拠となる機能IDも参照し、機能を複数の設計要素で実現する場合は分担を説明する。
検証ケースには担当する詳細設計項目、根拠となる詳細機能仕様・要件ID・機能ID・受け入れ条件IDを記録する。機能外の制約は実装・設計・出自等のレビューへ対応付ける。具体的な割り当てと検証結果は、それぞれを具体化する際に記録する。

変更時には、次を点検する。

1. 要件定義の全有効要件本文・主親表・本表の行が過不足なく一致し、同じ要件が複数行になっていない。主親の存在・単一性・循環なしを確認し、横断適用先を分けて扱う。
2. 機能定義が一意で、参照する機能・要件・受け入れ条件・未確定IDが存在する。すべての有効機能に根拠となる要件がある。
3. 親子を下位から確認し、親本文の全責務・全子・連携・横断条件を漏れなく照合する。要件ごとに必要な機能の組み合わせを確認し、機能本文の入力・正常時・境界・異常時の規則で要件全体を満たせるか判断する。足りない責務と未確定の規則を区別して残す。
4. 要件・機能の変更時は、分担・充足判断・根拠・残課題を再評価し、影響する設計・検証も更新する。単なるIDの関連付けを完了条件にしない。
5. 全分担の6工程経路と逆引きを確認する。未作成・未確定・参照不正を区別し、制約例外にも具体的なレビューケースを割り当てる。
6. 廃止IDの理由・後継と参照を更新する。行の追加・削除と第11.3節の件数も同じ変更で整合させる。
