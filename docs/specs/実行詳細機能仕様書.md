```trace
{
  "id": "spec-runtime#time",

    "DIR-REQ-0119"
  ],
  "upstream": [
    "DIR-FUNC-0001",
    "DIR-FUNC-0007",
    "DIR-FUNC-0009",
    "DIR-FUNC-0012",
    "DIR-FUNC-0014",
    "DIR-FUNC-0015",
    "DIR-FUNC-0018",
    "DIR-FUNC-0020",
    "DIR-FUNC-0021"
  ],
  "state": "confirmed",
  "pending": []
}
```

| 項目 | 採用規則 |
| --- | --- |
| 担当機能 | [イベント処理](../機能仕様書.md#dir-func-0012)が時刻を進め、[転送時間](../機能仕様書.md#dir-func-0015)が量から期間を計算する |
| 原点・型 | 実行開始を0とする相対時刻。`SimTime`は符号なし64bit整数のps。1秒=10^12ps、範囲0～18446744073709551615ps |
| 入力換算 | [設定仕様](設定詳細機能仕様書.md)の十進リテラルを十進有理数として厳密に換算。整数の分子・分母による換算結果が整数psかつ範囲内のとき受理する |
| 不適合値 | 負値、非有限値、0.1ps、上限超過は準備失敗。注：利用者指定時刻の暗黙の丸めは対象外 |
| 期間計算 | 非負整数ビット数N、正整数bpsのRに対し `ceil(N*10^12/R)` ps。商と余りから切上げる。十分広い整数の検査付き中間計算を使用し、最終値・時刻加算のあふれを検出する |
| 算術の失敗 | 入力・事前計算で判明するあふれは準備失敗、実行中に初めて判明する加算等のあふれは実行失敗。注：wrap・飽和・暗黙の打切りは対象外 |
| 表示 | 時刻・期間はps整数の十進文字列として結果へ保存する。全桁の整数精度を保持する |
| 精度 | 切上げ1回あたり誤差は0以上1ps未満。CANのEOF・解放は各々SOFから計算する。注：ビットごとの丸めやEOFから再度間隔を足す方式は対象外 |
| 例 | `0.001ns`=1psを受理、`0.0001ns`を拒否。N=1、R=3なら333333333334ps。上限時刻+1psは実行失敗 |

```trace
{
  "id": "spec-runtime#event-order",
  "stage": "spec",
  "requirements": [
    "DIR-REQ-0007",
    "DIR-REQ-0030",

    "DIR-REQ-0040",
    "DIR-REQ-0041",
    "DIR-REQ-0045",
    "DIR-REQ-0046",
    "DIR-REQ-0105",
    "DIR-REQ-0108"
  ],
  "upstream": [
    "DIR-FUNC-0001",
    "DIR-FUNC-0011",
    "DIR-FUNC-0012",
    "DIR-FUNC-0013",
    "DIR-FUNC-0016",
    "DIR-FUNC-0017",
    "DIR-FUNC-0023"
  ],
  "state": "confirmed",
  "pending": []
}
```

| 項目 | 採用規則 |
| --- | --- |
| モデル識別 | 正規化された完全インスタンスパスをUTF-8バイト列の辞書順で比較する。初期版は静的インスタンスのみ。注：ポインタ・hash表の反復順・OSスレッド順に依存するID生成は対象外 |
| 初期化 | 全インスタンスの初期化を1回ずつ完了してから時刻0を処理する。初期イベントは初期化順と各モデルの登録順で連番を付ける。初期化中の即時通知もキューに置く |
| イベント識別 | `(time_ps, delta, phase, sequence)`を処理順とする。sequenceは0始まりの単調増加u64で、成功した効果バッチの登録呼出し順に付与。複数配送先は正規パス順、複数負荷は同時刻の発火をまとめるdispatcherがgenerator ID順、同じgeneratorの明示時刻重複は入力配列順で予約する |
| phase 0 | 既に予定されていた転送完了・処理完了・資源解放。処理完了からキュー格納や受信配送が生じる場合はphase 1に通知する。CANのEOFと解放が同時刻ならEOFを先に登録する |
| phase 1 | 生成、キュー到着、受信配送、Timer通知。phase 0から発生した同時刻通知も含め、phase 1の追加がなくなるまでFIFOのsequence順で処理する |
| phase 2 | 調停。各資源を正規パス順に1回評価し、phase 1までにreadyになった候補集合を採取して不可分に選出・送信開始する。バスが占有中なら候補を次回の解放まで保持する |
| 同時刻への追加 | 現在phase以上への予約は同deltaへ置く。現在phaseより前への予約はdelta+1へ置く。phase 2で生じた処理・配送は次deltaへ置く。将来時刻はdelta=0から始める。各deltaのphase 1が空になった後でphase 2へ進む |
| ゼロ遅延 | phase 1のゼロtxProcessingDelayは同phaseにready通知を予約する。全ての同時生成が候補になる。phase 2終了後の新しい候補は進行中転送を奪わず、次回解放まで待つ |
| 過去時刻 | 現在時刻より過去へのTimer・配送・完了予約は実行失敗。同時刻の正当な予約は上記delta規則で受理する |
| 進行監視 | `max-events`既定100000000（実行全体で処理したイベント数）、`max-delta-cycles`既定1000000（同一時刻のdelta反復数）。次の処理で上限を越える場合は診断E-0004で実行失敗。同phaseの無限連鎖もイベント数上限で停止する |
| 連番・カウンタ | sequence・delta・イベント数のあふれはE-0004。失敗時は診断と部分結果の終了処理へ移る。上限設定と到達数をメタデータへ残す |
| 非プリエンプション | 調停結果を確定したSOF以後は、優先度の高い後着にも送信を継続する。後着は次の解放機会の候補になる |
| 拡張境界 | phaseの意味は汎用の完了・入力・調停。注：コアの比較キーへのCAN IDやCRCの組込みは対象外。資源モデルが候補と優先規則を与える |

### 2.1. 予約・仲裁集合・コミットの詳細

| 項目 | 呼出し条件・結果・不変条件 |
| --- | --- |
| 初期予約 | initialize中はnow=0、delta=0。登録されたイベント種別に対応するphaseで初期イベントを予約する。initialize成功順に効果をコミットし、全initialize成功後に実行へ移る |
| イベント種別 | RegistryのEventDescriptorにschema名、schema版、配送phase（0又は1）、payload検証器を登録する。一般Timerはphase 1、完了はphase 0。phase 2は仲裁要求からエンジンが生成する内部イベント |
| 調停要求 | `request_arbitration(resource_id)`は現在時刻のdirty集合へ追加する。phase 0/1からの要求は現在delta、phase 2からの要求は次deltaへ置く。同一時刻・delta・資源の重複は一件へ合流する |
| 仲裁の予約 | phase 0/1の現在deltaのイベントが尽きた時点でdirty集合を封じ、資源の正規パス順にphase 2イベントのsequenceを付与する。各資源は一回だけ評価する。これにより通常のイベントキーと資源順が一致する |
| 仲裁予約の一括検証 | dirty集合の封鎖では全資源分のsequence・メモリを先に検証し、全予約の公開成功時だけdirtyを消費する。失敗時はdirtyを保持して終了。未実体化の資源ごとに論理イベント1件を残件へ算入し、診断phase=run、time_ps=封鎖対象時刻、event_seq=nullとする |
| 待機の再評価 | readyへの遷移又は資源解放が調停を要求する。busy資源の調停は候補を保持して完了し、再評価契機は次のready又は解放。注：同時刻でのbusy待ちの反復予約は対象外 |
| 同時刻の戻り | phase 2から発生した配送・完了・新たな調停要求は次deltaへ置く。他のphaseでは、予約先phaseが現在phase以上なら同delta、前なら次delta。将来時刻のdeltaは0 |
| 成功単位 | 一つのイベントについてContextの予約・取消し・調停要求・計測更新を一つの効果バッチに蓄積する。callback成功後に参照・時刻・schema・カウンタ・必要メモリを事前検証し、全効果を一括公開してcommitted_eventsを1増やす |
| 失敗単位 | callback又は事前検証が失敗した場合は効果バッチを破棄して全実行を停止。出力snapshotは直前までのコミット済みjournalを正とする。モデル内部に途中更新があっても停止後は再実行せず、結果の読出し元はjournalとする。注：任意モデルの内部状態のロールバックは要求範囲外 |
| 失敗イベント | 候補をヒープから取り出しても、成功コミットまでは実行中の未処理候補として保持する。失敗時のpending_eventsはこの候補を含む。last_event_time_psは最後の成功コミットの時刻とする |
| キャンセル | TimerTokenは所有モデルIDと実行内0始まりu64連番で識別する。所有者による未処理tokenの初回取消しはtrue、発火済み・取消済み・未知・別所有者はfalse。取消効果はバッチ成功時に反映する。取消済みヒープ項目は取り出して捨て、処理数・残件・時刻へ影響する対象から除く |
| 仮token | 同一callback内で予約したTimerも返却tokenで取り消せる。予約と取消しを呼出し順にバッチへ適用し、取り消した予約は有効イベント数0。tokenは再利用を避けて単調に付与し、バッチ失敗時は全実行の終了に伴い失効する |
| max-events | 正常コミットN件まで許可する。次の有効イベントがT未満でNが設定値なら、そのイベント実行前にE-0004。次候補がT以上又は候補なしなら正常終了判定を優先する。初期化・取消済み項目・集計窓作成は件数の対象外 |
| max-delta-cycles | 各時刻でdelta=0を最初の1回と数え、`delta < max-delta-cycles`を実行条件とする。上限1はdelta 0まで許可する。次deltaが上限ならイベント実行前にE-0004。時刻が変わればdeltaを0へ戻す |
| 連番のあふれ | sequence/tokenはu64最大まで付与可能。次のIDが必要になった時点でE-0004。比較とカウンタ計算にはあふれ検査を適用する |
| journal | 初期状態と要求・受信・キュー・資源・計測の成功更新をエンジンが所有する。モデルはContext経由で観測用更新を提示する。出力側はjournalの確定状態を読み、停止したモデルへ状態を問い合わせる操作は対象外 |
| 詳細設計 | [実行詳細設計書](../design/実行詳細設計書.md#dispatch)の所有権・batch公開手順に対応する。ケースの入力と期待値は[共通実行検証仕様書](../verification/cases/共通実行検証仕様書.md)に記載 |

```trace
  ],
  "upstream": [
    "DIR-FUNC-0011",
    "DIR-FUNC-0012",
    "DIR-FUNC-0013",
    "DIR-FUNC-0015",
    "DIR-FUNC-0023"
  ],
  "state": "confirmed",
  "pending": []
}
```

| 項目 | 採用規則 |
| --- | --- |
| 型付き通知 | 登録済みの名前空間付きイベント種別と版、対象インスタンス、時刻、型付きpayloadを持つ。Timerとポート受信を区別してモデルへ通知する。未知種別・payload不一致・存在しない対象は診断する |
| Timer | 予約時に所有モデルと一意のtokenを保存し、発火時に同じモデルへtoken付きで通知する。取消しは未処理tokenのみ1回有効。取消済みtokenの再取消しは結果false、通知は1回限りとする |
| 接続経路 | 登録された出力ポートから入力ポートへ配送する。channelごとの状態・パラメータを分離し、各接続が独立した状態を保持する |
| CANとの分担 | CANの候補登録はバスモデルへの制御通知として即時に集約する。channelの遅延は成功フレームの受信観測へ適用する。詳細は[CAN時間仕様](models/CANモデル詳細機能仕様書.md#wire-time) |
| 終了後 | 終了時に残ったイベントは未処理として保存する。終端フックからのイベント予約は拒否する。結果は停止時の確定状態から生成する |

```trace
{
  "id": "spec-runtime#termination",
  "stage": "spec",
  "requirements": [
    "DIR-REQ-0024",
    "DIR-REQ-0031",
    "DIR-REQ-0042",

    "DIR-REQ-0055",
    "DIR-REQ-0095",
    "DIR-REQ-0096",
    "DIR-REQ-0120"
  ],
  "upstream": [
    "DIR-FUNC-0001",
    "DIR-FUNC-0007",
    "DIR-FUNC-0012",
    "DIR-FUNC-0014",
    "DIR-FUNC-0018",
    "DIR-FUNC-0019",
    "DIR-FUNC-0020",
    "DIR-FUNC-0023"
  ],
  "state": "confirmed",
  "pending": []
}
```

| 条件 | 結果 |
| --- | --- |
| 終了時刻 | INIの非負durationを原点0へ加えたT。通常の観測区間は常に`[0,T)`。時刻Tのイベントは未処理として残す |
| T=0 | 初期化・準備検証は実施する。生成・送信を含むイベントは0件。正常な時間打切り、finish_time=0、比率のゼロ分母は結果仕様に従う |
| 次イベントがT以上 | 予約されたイベントを未処理として保存し、finish_time=T、reason=`time_limit`。時刻Tまで資源状態の時間積分を行う |
| T未満でキューが空かつ全generatorの有効な発火候補を消化済み | reason=`events_exhausted`、finish_time=T。last_event_timeは最後に処理した時刻（0件ならnull）。その時点の資源状態をTまで維持して積分する。注：集計のための架空の終端イベントは対象外 |
| フレームの切断 | t_EOF=Tなら送信中のままとする。処理中・待機・送信中の要求をそれぞれ未完了として保存する。t_EOF<Tだが受信処理完了がT以上なら送信成功と受信未完了を別々に保存する |
| 周期負荷 | 生成件数はT未満に発火した周期要求のみを数える。終了理由の判定ではT以後に有効な発火候補が残るgeneratorを将来予定ありとみなし、time_limitとする。境界外イベントは物理キュー格納を省略できる |
| 正常終了時 | 未処理イベント数、未完了要求、資源状態、終了理由、T、last_event_timeを保存して終了処理を1回行う。未完了状態を保持する |
| 実行失敗 | failure_timeまでの処理済みイベントprefixと状態を部分結果として識別する。同時刻の残イベントは未処理状態を保持する。partial=true、処理連番と診断の失敗phaseを保存し、正常な全区間集計と区別する |

| 条件 | 期待結果・確認先 |
| --- | --- |
| バス解放が100us、A/Bのreadyも100us | phase 0で解放、phase 1でA/Bを格納、phase 2で既存待機も含めて仲裁する。解放イベントの登録順による候補欠落がない |
| 100usのphase 2でAが送信、次deltaで高優先B到着 | Aを継続しBを待機。確定済の仲裁結果を保持する |
| 同時刻のゼロ遅延Timerが自己再予約 | phase 1をFIFOで繰返し、max-events超過前にE-0004。シミュレーション時刻は進めず部分結果を返す |
| T=100us、EOF=100us | EOFが対象区間外のため送信中。EOF=99999999psなら成功。同時刻の結果判定は処理連番で一致する |
| 10usでイベント枯渇、T=1ms | finish_time=1ms、last_event_time=10us、reason=events_exhausted。残る990usも積分区間に含む |
| 検証範囲 | 上記は仕様上の期待値。受け入れ条件は要件定義書の時刻順・同時刻・終了の項目へ対応し、エンジン実装試験は未実施 |

## 拡張モデルと同時刻

| 項目 | 規則 |
| --- | --- |
| 資源の独立 | GWの各CAN bus、AXI Interconnect、Ethernet全二重の各方向送信器は別resource_id。dirty封鎖はそのID順で行い、各資源のready・busyを別に評価 |
| clock | AXIのclock_periodとREADY列はAXIモデルが正確psの有効edgeへ変換する。コアの時刻キーとphaseは共通仕様を適用 |
| 初期化 | simpleの初期化後、profile coordinatorを対象正規パス順に初期化し、その後に時刻0を処理する。coordinatorが無い既定CANの順序は従来どおり |
| 半二重 | Ethernet v2では媒体単位のresource_idが両端を同時評価する。carrier到達・jam完了・再試行をモデルイベントへ変換し、同一時刻の候補全件を評価してから開始を確定する。phase/deltaの具体境界は[媒体設計](../design/Ethernet媒体拡張詳細設計書.md)を適用 |
| 終了 | 全profileで[0,T)、実行失敗のコミットprefix、未完了の保存を共用。GW複製・Ethernet送信方向・AXIhandshakeは各モデルで成功単位を具体化 |
| generator | schema2にも同時生成のgenerator ID/ordinal順と論理将来候補の終了判定を適用する |
| 正本 | [拡張共通仕様](拡張モデル共通詳細機能仕様書.md)、[統合詳細設計](../design/複数モデル統合詳細設計書.md) |
