現行0.1.0の提供対象はClassical CANの`can.cc.ideal.v1`である。本書の追加profileは将来対応モデルの準備・実行・結果を接続する仕様契約であり、profile名や確定仕様の存在は製品での提供・実行検証完了を示すものではない。提供時期と対象範囲は[要件定義書](../要件定義書.md)の将来対応予定を管理元とする。

[機能追加と契約の維持](../要件定義書.md#dir-req-0122)に対し、本書はprofile単位でvalidator・codec・metric・結果版を選択する責務を具体化する。各モデルは固有の入力、状態遷移、成功／破棄、観測点を担当し、共通基盤は[構造と値の解決](設定詳細機能仕様書.md#values)、[イベント順と成功コミット](実行詳細機能仕様書.md#event-order)、[停止と診断](診断詳細機能仕様書.md#lifecycle)、[保存](結果詳細機能仕様書.md#atomic-output)を担当する。モデルの親要件の充足は、子要件に対応する固有規則とこの共通処理が接続する振る舞いで確認する。

| 入力 | 書式・処理 |
| --- | --- |
| workload共通 | `{schema_version:2,generators:[Generator...]}`。UTF-8 JSON、ルートのこの2キーを必須とする。Generatorは共通id・kind・nodeとkind固有キーから成る |
| id / kind / node | idは`[A-Za-z_][A-Za-z0-9_]*`で全体一意、kindは名前空間付き登録文字列、nodeはNED展開後の正規モデルパス。配列順と区別してgenerator IDのUTF-8辞書順を使用 |
| 同時生成 | 同一時刻の全generator発火をdispatcherがまとめ、(generator ID,ordinal)順でphase1へ予約する。request_idの基本形は`generator_id:ordinal`。転送コピーとhopのIDはモデル仕様に従う |
| GW | CANの既存periodic/explicit generatorのfieldsをschema2で受理。入力互換のためschema1も同じ生成意味で受理し、選択したGW profileの構成検証を適用する |
| 追加モデル（GW以外） | schema2を必須とし、それぞれのモデル仕様のkind/fieldsを受理する。未知profile/kind/schemaは準備失敗 |
| workload省略 | 空のgenerator配列を選択する。構造・model-configの完全検証と初期化は実施し、終了理由・初期計測は既存契約に従う |
| 読込順 | CLI/INI→選択profileの存在→NED構文・descriptor・値・接続→model-config構文／schema→workload構文／schema→profile横断検証→factory/initialize。未取得ファイルは共通input_unreadable診断 |
| 検証の優先 | 各入力はファイルsource位置順、重複の二つ目を対象。解決済み対象は正規パス順、設定配列の値違反は入力index順。複数違反は最初の確定primaryと、その時点までの診断を保存 |
| profile診断 | E-0001の`unsupported_profile`、`unsupported_profile_setting`、`model_config_invalid`、`workload_invalid`、`topology_invalid`を追加し、詳細原因をdetails.rule/targetへ保持。既存のinput_unreadable/unknown_type等が直接該当する場合は既存理由を優先 |
| 実行失敗 | codec/schema不正はE-0002 invalid_event、モデル状態不変条件はE-0002 model_failed、時刻・ID等の上限はE-0004。通常のqueue満杯やAXI応答エラーはモデル上の結果として記録 |
| 再現情報 | sourcesへlogical_path=`model-config`としてmodel-config raw bytes・path・SHA256を追加し、configには確定model-profileとmodel-config参照を含める。モデル別初期状態と設定を各schemaのcanonical JSONで記録 |

| 項目 | 契約 |
| --- | --- |
| 版の選択 | 既定CANは出力schema1、本書に登録する追加profileはschema2。CLIのrun/validate要約schemaは既存版1を保持し、ファイル側の結果版はmanifest/resultsで識別 |
| ファイル集合 | manifest.json、results.json、events.csv、summary.csv、diagnostics.jsonl。原子的公開・hash・文字・数値表記は既存結果仕様を適用。manifest/results/CSVのschema_versionは2。診断レコード自体のschema_versionは1を保持 |
| results.json | `{schema_version:2,run_id:S,metadata:Metadata2,simulation:Simulation2}`。S/D/N等の型は既存結果仕様と同じ |
| Simulation2 | `{termination:S,partial:boolean,start_ps:D,end_ps:D,last_event_time_ps:D?,committed_events:D,pending_events:D,records:Record[],summary:Record[],model_records:ModelRecord[]}`。共通のRecordと17列CSV・観測順は結果仕様を継承。注：CAN専用のrequests/receivers配列はschema2のキー集合の対象外 |
| ModelRecord | `{schema_name:S,schema_version:N,record_id:S,subject:S,request_id:S?,origin_request_id:S?,time_ps:D,data:object}`。すべて必須。Nは登録済みの正整数JSON number。schema_name/版でdataを解釈する。各profileはschema_nameごとに版を一つ固定し、同じ名前の異なる版を一実行へ混在する方式は対象外（注） |
| 保存意味 | ModelRecordはモデルが最後にコミットした状態のsnapshot。一意キーは(schema_name,record_id)、保存順は(schema_name,subject,record_id)のUTF-8辞書順。time_psは最後の成功更新時刻。初期値は0。時系列の履歴が必要な量は共通records又は独立した転送／handshakeレコードへ保存 |
| 要求関係 | request_idは当該操作に対応する要求識別子、origin_request_idはモデルで定義する元要求又はnull。dataの各参照は同じrun内のrecord又は入力設定へ対応付ける |
| Metadata2 | 既存Metadataの全必須キーに`model_profile:S`と`model_schemas:[{schema_name:S,schema_version:N}]`を追加する。Nは登録済み正整数JSON number。model_schemasは選択profileの全登録出力schemaを名前順に一度ずつ記録 |
| 指標 | metadata.metricsは選択profileが登録した指標の一覧を名前順に保持する。CANの37指標は既定CANの集合であり、他profileはそのモデル仕様で定義した集合を使用。unit/value_kind/sampling/aggregationの意味は共通 |
| GWレコード | can.request/1とcan.receiver/1のdataは旧Request/Receiverの外側キーを使用し、model_fieldsはGW仕様のMultibusFieldsへprofile別に分岐して、GW固有のforward履歴はgw.forward/1に置く。GWを通ってもCAN物理フレームの計算方式はcan.cc.ideal.v1の定義を使用 |
| AXI・Ethernet | dataの型、ID、生成契機・最後の更新は各モデル仕様の出力契約を適用し、コアはopaque objectとして保存する |
| 異常snapshot | 成功済みjournalだけを保存する。追加profile選択が確定した後の準備失敗はschema2と空のmodel_records/records/summaryを保存し、metrics/model_schemasは選択profileの登録集合とする。選択前のINI失敗又は未登録profileは既存schema1の準備失敗形式を使用する。Tで未完了のモデル状態はpending/active等の各モデルの列挙値で残す |
| 未知データ | 読み戻し時に未知のschema_name/版又はdata型違反は不正出力として診断する。解析器が対応schemaだけを選ぶ場合は、未解釈のschema集合を解析結果へ明示する |

## Ethernet媒体拡張の共通境界

| 項目 | 契約 |
| --- | --- |
| 媒体別選択 | Ethernet v2は一実行内でリンクごとに媒体とduplexを選択する。同じprofile内の半二重と全二重はSwitchで接続可能。異種プロトコル変換とは区別する |
| 衝突領域 | 半二重の一つの物理リンクは一つの共有collision domain。共有contextが両端のcarrier・送信試行・jam・再試行時刻を一括評価し、同時開始は衝突として記録する |
| 再現性 | CSMA/CDのbackoff乱数は明示seed・版付き決定的アルゴリズムから算出する。metadata.seedは正規十進文字列を保存。注：これは負荷生成の確率化とは別のMAC制御 |
| schema互換 | Ethernet v1の型登録・入力・結果を維持し、v2のcodec・record版は[媒体仕様](models/Ethernet媒体拡張詳細機能仕様書.md)に登録。共通schema2の包絡・CSV列は継承 |

## 将来対応モデルの登録条件

上記のモデル別正本に従い、profile・型・schema・metricを登録する。準備検証と実行状態はモデル側が所有し、共通の時刻・確定journal・出力契約を適用する。

| 共通条件 | 契約 |
| --- | --- |
| 入力・診断 | 各profileのmodel-configとworkloadを専用validatorへ渡す。型・必須キー・範囲・接続・参照を初期化前に照合し、違反を共通E-0001とdetails.rule/targetで示す |
| 結果・互換性 | 各モデルの版付きModelRecordをschema2へ格納し、実際に使用した入力hash、descriptor、時間定数を保存する。指標の単位・標本・集計・母数は各正本の登録を適用する。既存profileのschemaと既定CAN入力は保持する |
| モデル間の連携 | DDR/SRAMとDMAの同一実行内の連携はメモリ・IPC仕様のサービスを共有する。その他の将来profileは仕様で定めた構成を受理し、新しいプロトコル間変換は独立codecと複合profileで追加する |
