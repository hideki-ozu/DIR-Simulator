公開`Registry`はprofile、module、channel、event、metric、model record、coordinatorと戦略関数を静的登録する。`Registry::new()`は13組込みprofileを含み、`Registry::empty()`は外部登録だけを使う。`prepare_with_registry`は選択profileの登録参照とNED接続を照合し、組込みprofileを既存アダプターへ、それ以外の登録profileを`runtime/registered.rs`へ渡す。後者の結果は`output/registered.rs`がschema2へ変換する。登録APIの検証範囲は[拡張runtime検証記録](../verification/results/extension-runtime-2026-10-05.json)に記録する。

現行のCAN／CAN間Gateway入力は、公開`input::prepare`から内部`input/can.rs`アダプターを呼び、共通`input/ned.rs`の解決結果をCAN設定へ変換する。宣言・値・payload・profileの照合は内部`ModelRules`で共通処理へ接続し、Gatewayの構成照合は`input/gateway.rs`が担当する。共有データは`PreparedSimulation`と`Snapshot`の共通・CAN・Gateway部分へ分かれ、実行処理も`runtime/engine.rs`・`scheduler.rs`・`can.rs`・`gateway.rs`へ分かれる。これらは組込みモデルの専用処理として維持する。公開`Registry`は`registry/mod.rs`と`registry/prepare.rs`で登録・準備を担い、追加登録モデルは`runtime/registered.rs`の共通実行経路へ渡す。開発中ソースはEthernet L2/QoS/VLAN/媒体・100BASE-T1とCAN FDを専用input/runtime/output経路へ追加し、`PreparedSimulation`と`Snapshot`のoptionalモデル領域で所有を分ける。`PreparedSimulation`と`Snapshot`にはAXI・SoC・メモリ／IPCのoptional領域も追加し、各専用input/runtime/outputと共通CLIへ接続した。ファイル単位の境界は[入力・設定設計](入力・設定詳細設計書.md#1-担当境界とデータの寿命)を参照する。

<a id="planned-staged-adapter"></a>

### private staged-coordinator adapter

公開`Model::on_event/on_arbitration`はmutable callbackを呼んだ後でEngineがEffectsをcommitする現行のsignatureを保持する。新しい3 profileは次のprivate経路で同じFES・Registry ownership検証へ接続する。runtime/network.rsとruntime/registered.rsのprivate経路へ実装し、schema・算術・予約確保失敗を注入して成功prefixを確認する。

```text
NetworkState::event/arbitrate(committed_state, context) -> Result<NetworkDelta, Diagnostic>
NetworkArena::prepare(key, batch, next_id, sequence, snapshot, initial) -> ModelResult<PreparedNetworkEffects>
NetworkArena::commit(PreparedNetworkEffects, snapshot) -> ()
NetworkState::apply(NetworkDelta) -> ()
```

`NetworkDelta`は変更対象のframe/copy/reception/queueと、CAN変換の`BridgeDelta`、動的制御の`DynamicDelta`、TSNの`TsnDelta`を所有する。`runtime/registered.rs`の`NetworkArena::prepare`がFES・dirty集合・journal・schema・資源予約をpreflightし、commit時に差分を適用する。外部登録Modelのtraitと既存13 profileの呼出し経路は維持する。

plan/prepareでchecked時刻・ID・所有・schema・容量を照合し、Effectsと変更対象table partition・bufferの完成値を所有する。失敗する可能性のある生成・確保をここで終え、commit区間は予約済み値のmove/swapと整数代入だけでEngineとcoordinatorを一緒に確定する。commit中のmap挿入・Vec拡張に新規確保を残さず、通常経路で全model stateをcloneしない。allocatorがprocessをabortする失敗は回復可能なtry_reserve失敗の診断保証と区別する。失敗したplan/prepareは差分を破棄し、現イベント・committed state・journal・FES・参照閉包を直前成功prefixに保つ。

phase0 batchはcoordinatorが保有する同時刻の全completion/control/期限予定を集め、既存Engineのdelta/phase順序を保持する。phase2のdequeueで解放された容量の再offerは次deltaへ送り、同じdeltaの過去phaseへ戻らない。3 profileの共通hookは単独の製品適合ケースで失敗境界と確保後commitを確認し、各固有検証ケースでもqueue/token/credit/RX/epochの部分変更がないことを確認する。
