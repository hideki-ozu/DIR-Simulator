

| データ／処理 | 所有・手順・不変条件 |
| --- | --- |
| ProfileRegistry | profile名→ProfileDescriptorを固定mapで所有する。既定CANの登録と新profileの登録は独立したentry |
| PreparedProfile | 選択profile、入力snapshot、ResolvedModel、profile固有の不変設定、generator cursors、出力codecとmetricの登録集合を所有 |
| prepare | INIのmodel-profileを解決し、共通NED/設定validator後にprofile.validate(model_config,workload,resolved_model)を呼ぶ。検証成功後にだけモデルarenaとcoordinatorを構築 |
| ファクトリ | simpleは通常factory、compoundのGW coordinator等はprofile-ownedな実行オブジェクトとして別ID名前空間で登録する。構造compoundを汎用factory対象へ変更することは範囲注釈上の対象外 |
| coordinator ID | `@profile:<profile>:<正規対象パス>`を内部の文字列IDとし、NED simpleのIDと名前空間を分ける。ログ上のsubjectは対象の正規パス。初期化順はsimple全件後に対象パス順でcoordinatorを初期化し、全完了後に最初のイベントを処理 |
| 共有output | PreparedProfileはcoordinator→担当context→解決済output handle集合を凍結する。Engineはsend_atの所有集合・codec・経路を照合し、Envelope送信元には実output所有モデルを設定する。詳細は[Context契約](../specs/インタフェース詳細機能仕様書.md) |
| 選択検証 | 不適合なimplementation/protocol/capability、余分なdeviceや結線、未登録generatorをprofileが診断する。一般のNEDパーサは登録された記法と型を共通に処理 |
| 互換性 | profile省略の既存prepare経路とschema1を保持し、追加Registry entryによる既存CANのID・予約順変化を避ける。IDは当該実行の実体集合だけから採番 |

## 実行・計測・失敗

<a id="journal"></a>

```trace
{
  "id": "design-model-extension#journal",
  "stage": "design",
  "requirements": [
    "DIR-REQ-0159",
    "DIR-REQ-0160"
  ],
  "upstream": [
    "architecture#arch-model-extension"
  ],
  "state": "confirmed",
  "pending": []
}
```


| 構成 | 処理 |
| --- | --- |
| generator dispatcher | kindで登録decoderを呼び、次回候補だけを保持。時刻ごとの全候補を共通順でphase1に予約。model固有のeligible時刻やclock丸めは発火後のモデル状態へ反映 |
| 独立資源 | BusContext、AXI transaction context、Ethernet全二重方向別送信器と半二重共有媒体contextは各モデルが状態を所有。予約するtime/delta/phaseとdirty資源操作だけをEngineへ渡す |
| schema2 journal | key=(schema_name,record_id)の最新ModelRecordと共通計測器を保持。モデルの効果batchでcodec検査済みrecord upsertを適用。以前の行への上書きも成功コミット時だけ公開 |
| publish | model_recordsを正規順へ並べ、共通結果処理へSimulation2を渡す。CSVは共通計測のprojection、モデル詳細はJSONのdataが正本 |
| 検証 | Registryに存在しないschema、record_idのsubject変更、time_psが現在callbackのnowと異なる更新を実行不変条件違反として診断（initializeでは0）。同じnowでの複数更新は効果順で適用し、既存行の時刻は単調増加又は同値とする。schemaがimmutableとする項目の変更はモデルvalidatorで検査 |
| 終了 | EngineのT・上限・失敗prefixを共用。モデル全状態をsnapshotとしてexporterへ問い合わせる処理は対象外という注釈を適用し、成功journalからpartial結果を作る |
| 拡張 | 新しいprofileとschemaを別entryで登録。既存profileの識別子を別意味へ置き換えることは範囲注釈上の対象外。異種変換は将来の専用coordinator・codecで追加 |

| 確認 | 対応 |
| --- | --- |
| profile入力・互換性 | [統合検証仕様](../verification/cases/拡張モデル統合検証仕様書.md) DIR-TEST-0029～DIR-TEST-0030 |
| journal・時間・終了 | 同仕様 DIR-TEST-0031～DIR-TEST-0032 |
| モデル固有 | GW・AXI・Ethernetの詳細設計を正とし、本書は識別・所有・共通境界だけを担当 |

| 項目 | 統合契約 |
| --- | --- |
| 半二重の同時開始 | 一つの媒体resource callbackが同時刻候補をsnapshotしてから一括遷移する。出力ID順に先着一個だけへ所有を渡す方式は衝突評価の対象外（注） |
| 版検証 | ModelRecord.schema_versionは選択profileの(schema_name,version)集合へ一致させ、未知版を型不正として扱う。旧版dataの意味は維持 |

## 当初対象の統合境界

| 項目 | 設計 |
| --- | --- |
| 登録と入力 | [拡張共通仕様](../specs/拡張モデル共通詳細機能仕様書.md)の追加profileをProfileRegistryへ登録し、同じprepare/validate/run操作で呼ぶ。型とworkloadの許可集合・初期状態・結果schemaはprofileごとに固定する |
| 通信・共有資源 | CAN FDと100BASE-T1は既存通信モデルの抽象責務を再利用し、SoC／AHB／NoCは専用contextを持つ。DDR/SRAMとDMAはメモリ・IPC coordinator内の同じbyte領域と資源サービスを共有する |
| schemaと出力 | ModelRecordの登録名・整数版とmetric descriptorをprofileごとに保存する。共通CSV列・原子的公開・成功prefixは従来契約を適用する |
| 拡張の検査 | 追加profileの存在・正しい型／入力の受理・異なるprofileの型／schema拒否・出力登録集合を検証し、既存CAN、GW、AXI、Ethernetのfixtureを同buildで回帰確認する |
