| データ | 所有者・表現 | 不変条件 |
| --- | --- | --- |
| SimTime / Duration | u64 ps。入力は正確な十進有理数、中間積はchecked u128以上 | 最終値をu64へ範囲検査して変換 |
| EventKey | (time_ps:u64, delta:u64, phase:u8, sequence:u64) | 昇順辞書比較。sequenceは予約順であり実行順とは別 |
| FutureEventSet | Engine所有の最小ヒープ | キーが同じ二イベントはsequence一意性で区別 |
| Event | key、target、port任意、schema名・版、所有bytes、TimerToken任意 | keyとpayloadは予約後に固定。対象とschemaは予約前検査 |
| dirty | (time,delta)をキーとした正規resourceパスの順序集合 | 同一資源の重複要求は一件へ合流 |
| active_tokens | token→予約済み／取消済みの状態表 | 有効ヒープ件数から取消済みを除いた値を保持 |
| current | 次の実行候補一件、成功処理件数、最後の成功時刻 | pop後commit前のcurrentも未処理件数へ算入 |

| 処理 | 手順・結果 |
| --- | --- |
| 予約キー | future timeはdelta0。現在時刻では実行仕様のphase規則からdeltaを定める。phase2はdirty封鎖時だけ生成。相対時間はchecked now+delay |
| 次の仕事 | 有効ヒープ先頭とdirtyの最小(time,delta)を比較する。その組のphase0/1を全部処理後、dirty資源の正規パス順でphase2を一括予約。ヒープが空でもdirtyがあれば調停を処理する |
| dirty封鎖の失敗 | phase2全件の連番・確保メモリを検査して一括予約し、成功時だけdirty集合を消費する。失敗時は元のdirtyを保持し、診断phase=run、time_ps=対象のdirty時刻、event_seq=null、details.operation=seal_arbitrationを記録する。未実体化dirtyの資源件数をpending_eventsへ含める。連番上限はE-0004、検出可能なメモリ確保失敗はE-0002 model_failed |
| 未登録の順序 | 一イベントの予約コマンド順を保ち、成功バッチごとに連続sequenceを割り当てる。取消しでsequenceは再利用する対象外。hashの反復順は使用対象外という注釈を適用 |
| 終了の判定順 | 入力・初期化完了後T=0を判定。次候補がT以上又は論理generator将来予定だけならtime_limit。候補・dirty・論理予定が全て空ならevents_exhausted。それ以外は上限検査して候補を処理 |
| 上限 | committed_events==max-eventsの時に次のT未満候補を処理しようとすると失敗。delta>=max-delta-cyclesも同様。失敗候補をcurrentに保持して停止snapshotへ渡す |
| 空時間 | 計測器は前状態を次の観測点まで積分し、実イベントのない期間は仮想イベントの生成対象外。正常終端は必ずT |
| 複雑度 | ヒープ挿入・取出しO(log E)、dirty追加O(log R)。初期周期列は各generatorの次回一件を保持し、全期間の配列化は対象外 |

実行条件から渡されたT、計測窓、単位付き時間は準備時の正確換算値を保持し、schedulerで再解釈しない。量と帯域からの所要時間は正確有理数からceilで整数psへ一度変換し、開始時刻との加算を検査する。正常終了の観測終端はT、異常時は結果仕様のHであり、最後の成功イベント時刻とは別フィールドで結果処理へ渡す。DIR-TEST-0007で値・予約時刻・停止snapshot・時系列の終端の一致を確認する。

| 構成 | 内容・所有権 |
| --- | --- |
| Engine | モデルarena、Registry、接続表、FES、dirty、CommittedJournalを単一実行スレッドで所有 |
| Model arena | 実行モデルを安定IDで管理し、一callbackずつ可変参照を渡す。複数CAN adapterの共有状態はモデル層BusContextとして別途管理 |
| EffectBatch | schedule/cancel/send/dirty/observation/state_updateを呼出し順で蓄積する一イベント限りの所有値 |
| CommittedJournal | 要求・受信・キュー・資源の最新観測状態と集計器、追記済み時系列。Engineだけが公開更新を行う |
| FinishContext | frozen snapshotと終了状態の読取参照。解放処理で生成した診断は別の診断集合へ追記 |

| 段階 | 処理・失敗境界 |
| --- | --- |
| dispatch | 予約済みbytesをschema codecで検証・復号して対象callbackへ渡す。ポート受信は入力portを含め、自己Timerはtokenを含める |
| collect | callbackは自モデルを更新しつつContextへ効果を提示できる。CANモデルは必要な計算・不変条件を先に検査して最小差分を適用する。Contextの効果はこの時点では未公開 |
| prepare_commit | callbackが成功したら、全コマンドを仮状態へ順に適用して参照・時間・容量・連番・schemaを検査する。新規キュー要素・journal差分に必要なメモリを確保する |
| publish | 検査済み差分だけをFES、dirty、token表、journalへ移す。ここを一つの論理コミットとする。成功イベント数とlast_event_timeを更新する |
| 記録 | 出力用時系列を成功コミット順に追記可能な一時spoolへ流し、要求台帳等は結果処理側で一時ファイルへ分離できる。出力失敗は診断仕様のE-0003として処理する |
| callback/検査失敗 | バッチを破棄し新しいcallbackの開始を終了する。FES・dirty・journalのコミット済み状態と未処理currentを凍結する。任意モデル内部をロールバックする義務は対象外という注釈を適用 |
| 終了処理 | initialize成功済みの実行オブジェクトへ初期化の逆順でfinishを通知。simpleのみなら逆安定ID順、追加profileのcoordinator順は本書末尾を適用。finishは資源解放だけを実行し、出力値はjournalから取得する。一次失敗を保持し二次診断を記録 |
| ランタイム異常 | モデルが返すModelErrorと検出可能な算術・予約・型エラーは構造化診断へ変換する。注：OSによる強制終了やプロセスabort後の部分結果公開は提供保証の対象外 |

| 責務 | 参照 |
| --- | --- |
| 個別record順序・effect_seq・異常終端H | [結果仕様](../specs/結果詳細機能仕様書.md) |
| 準備失敗・finish失敗・出力失敗の優先 | [診断仕様](../specs/診断詳細機能仕様書.md) |
| SOF/EOF/受信状態の更新 | [CAN詳細設計](CANモデル詳細設計書.md#state-machine) |

同じ初期イベント集合からdispatchしたとき、callbackの順序だけでなく予約コマンド順・effect_seq・journalの差分順も一致させる。成功したphase0/1だけを次の仲裁集合へ反映し、失敗したバッチが予約集合や計測値へ漏れないことをDIR-TEST-0009で確認する。これが離散イベント実行と再現性の親責務に対する配送・Context側の分担である。

| 処理 | データ・手順 |
| --- | --- |
| Registry作成 | 順序付きmapでmodule/channel/event/policy/generator/metric/exporterの登録を保持。module/channelはimplementation_key単独の重複を準備失敗とし、event/policy/generator/metric/exporterは識別子と版の組の重複を準備失敗とする。model実装キーとNED完全修飾名の対応は別map |
| 構造解決 | NED AST→型表・実装キーとdescriptor照合→選択networkの静的展開→INI値→接続経路検証→CAN構成検査の順。具体的な入力診断順はNED・設定仕様を適用 |
| NodeId | compound展開後のsimple実行インスタンスの正規パスをUTF-8順に並べ、0始まりu64へ割り当てる。結果へは正規パスを出す。compound/rootの構造IDは別名前空間 |
| PortId / ConnectionId | ownerパス・port名／親パス::始点表記を正規ソートして各名前空間で0始まりu64を付与。NED内部の宣言順と分離 |
| channel状態 | 明示した辺ごとにfactoryから作成。再利用したNED型のparameterと実行状態は辺別所有。CANはpropagation-delay能力のdelay_psだけを受け取る |
| 型の対応 | portの(protocol,message,schema版)を比較し、schema名をprotocol+'.'+messageへ解決。EventDescriptorの検証器はpayloadを所有型へ復号してモデルへ渡す |
| モデル追加 | 別crateで新schema・factory・policyを登録し、既存コアのヒープ比較・PS時刻・journalの共通ヘッダを使用する。CAN固有fieldの比較はCAN実装へ閉じる |
| 結果拡張 | profile/schema版でモデル別snapshotとmodel_fields codecを選ぶ。metric/exporterも登録記述から呼び出し、意味を変える追加は別識別子又は版へ分離 |
| 構築順 | 登録集合と全入力を検証後、安定NodeId順にfactoryを呼び、initializeを同じ順で実行。factory失敗時もそれまでの資源を逆順に解放 |
| 実装単位 | 初期はsim-core、sim-model、ned-parser、sim-config、sim-runtime、sim-can、sim-result、dir-simulatorのcrate境界を目安にし、具体的な内部module分割は同じ依存方向で実装する |

共通ノードに送受信・キュー・仲裁などの能力を組み合わせる際は、Registryのdescriptorを固定した後にモデルが同じ実行Contextを使用する。CAN固有の要求フィールドや優先キーを共通ヒープへ追加せず、BusContextの比較規則に閉じる。追加payload/channel/policyの登録と独立資源の同時動作はDIR-TEST-0010で確認し、既存CAN入力の回帰を合わせてDIR-REQ-0019・0051・0122の分担を満たす。

外部の受理・計測規則は[資源仕様](../specs/資源詳細機能仕様書.md)を正とする。以下は状態所有と更新手順であり、CAN固有の仲裁キーは[CAN設計](CANモデル詳細設計書.md#state-machine)から渡す。

| 内部状態 | 所有者・不変条件 |
| --- | --- |
| QueueState | 資源所有モデルがcapacity、policy、待機requestと生成順を所有。0≤len≤capacity、requestは一キューに一度。candidate参照は読取専用 |
| ResourceState | 資源IDごとにowner、busy開始、EOF、releaseを保持。CANのtransmitting/intermissionを分け、別busのownerや解放予約を共有しない |
| Transition | 取出し、owner、状態、予約、観測の局所差分。時間・容量・ID・予約を検査し終えた一つのEffectBatchへ渡す |
| DelayBreakdown | generated/ready/SOF/EOF、受信者ごとのobserved/rx_completeを保持。TX処理、待ち、wire、経路、RX処理の担当を分ける。busy終端はreleaseで、受信終端とは別 |
| 確定観測 | 長さの前後値、容量、要求、時刻、連番、busy区間は成功commitで公開。[結果処理設計](結果処理詳細設計書.md)はこれを積分・集計し、モデルの途中変更を読み出さない |

| 操作 | 手順・失敗境界 |
| --- | --- |
| offer | ready到達時の確定lenとcapacityを比較。空きなら格納、満杯なら新着だけqueue_full。capacity=0も同じ判定。候補提示・仲裁敗北ではlenを変更しない |
| arbitrate | idle時に同時刻のready集合を確定し、モデルの優先キーで選ぶ。選出要求の時間・EOF/release予約を先に検査し、take_winner・owner設定・観測を一括確定 |
| EOF / release | EOFでsuccess・受信通知を確定し、ownerを保持してintermissionへ進む。releaseでidleへ戻し再仲裁を要求。後着の高優先要求で既存ownerを置き換えない |
| 遅延 | 待ち=SOF-ready、wire=EOF-SOF、伝搬=observed-EOF、RX=rx_complete-observed。ローカル候補待ちと共有資源待ちを二重加算しない。checked加算失敗は公開前に全体停止 |
| 打切り・失敗 | T以上の予定完了を実績化せず、確定prefixと残状態を保存。失敗バッチが内部を変更していても結果はjournalのみから作る |

[DIR-TEST-0082](../verification/cases/利用フロー・品質検証仕様書.md#dir-test-0082)で容量、競合、非プリエンプション、独立資源、時間成分と失敗注入を確認する。計測式の判定は結果処理検証へ分担する。

| --- | --- |

| 制御段階 | 手順と境界 |
| --- | --- |
| validate | CLI字句を検証しprepareを実施。成功時は件数付き検証要約をstdoutへ返しexit0。factory/initialize/on_event/finishは呼ばない |
| run準備 | 出力先が新規又は空で親が存在することを確認し、prepare→allocate→factory→initializeを行う。既存出力非空はexit4、入力取得不能・値域違反はexit2としてイベント実行前に終了 |
| 初期化失敗 | 予約を全取消し、成功済だけにfinishを逆順通知し全allocate済資源を解放。未検証入力・途中初期化状態を実行や計測へ流さずprep_failedを返す |
| 実行 | dispatcherとschedulerの固定順で実行し、成功バッチだけを計数。正常T境界と枯渇はexit0、runtime不正はexit3。時刻Tのイベントは処理せずpendingへ残す |
| 終了・解放 | 新callback開始を止めsnapshotを凍結し、全初期化成功済のfinishと解放を継続。finishが失敗しても残りを解放し、一次診断を上書きせず二次診断を追記 |
| 公開 | [結果処理設計](結果処理詳細設計書.md)へsnapshotと診断を渡す。出力失敗があれば最終exit4を返す。成功manifestの有無とterminationを別々に確認する |
| CLI出力 | run成功/失敗のstdout・stderr・終了コードは操作仕様の字句・標準出力契約に従う。利用者はmanifestとRunReportを読み、部分結果と実行状態を判別する |
